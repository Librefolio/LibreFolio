# Decision: a two-level asset-type taxonomy

## Context

`AssetType` (`backend/app/db/models.py`) holds eleven base values — `STOCK`, `ETF`, `BOND`, `CRYPTO`, `FUND`,
`CROWDFUND`, `HOLD`, `COMMODITY`, `REAL_ESTATE`, `INDEX`, `OTHER` — and seven subtypes:

- six ETF subtypes, `ETF_STOCK`, `ETF_BOND`, `ETF_COMMODITY`, `ETF_REAL_ESTATE`, `ETF_CRYPTO`, `ETF_MONETARY`, added
  with the risk taxonomy (`00d8c735b`, 2026-09-18);
- `CROWDFUND_REAL_ESTATE` (property-backed crowdfunding loans), added by workstream K (`4041ffa98`, 2026-09-24;
  developer request R17). No migration: the column stores the enum's string.

(`CROWDFUND` was called `CROWDFUND_LOAN` until 2026-07-06.) A subtype answers one question — *which base type does
this instrument contain?* — so the second level is the set of base types, not a parallel taxonomy. Two families have
one, `ETF` and `CROWDFUND`; their plain values stay selectable as the residual for mixed or unstated content.
`ETF_MONETARY` is the one subtype with no base-type counterpart: cash is an account balance, not an asset.

## Two views, one map each

| View | Question | Map / helper | Used by (at `083ed26dc`) |
|---|---|---|---|
| **Family** (container) | "which kind of instrument is it?" | `ASSET_TYPE_FAMILY`, `assetTypeFamily()` | the type select's tree; both allocation charts (pie and history) since workstream I's D15 |
| **Content** | "what does it contain?" | `PRIMARY_TYPE_MAP`, `primaryAssetType()` | the pastille icon (`ASSET_TYPE_CONTENT_ICON`) and the badge colour — the gate asserts `badge(x) = badge(primary(x))` |

An unknown value resolves to itself, never to `OTHER`, so a new enum value stays visible and the enum gate complains.
The analysis of D-K3 expected the allocation pie to file `CROWDFUND_REAL_ESTATE` under Real estate (by content); the
charts moved to the family view afterwards, so at HEAD it sits in the Crowdfund group. No chart groups by content.

**Provider comparison (R18, step 17).** When a provider proposes a type for an existing asset, a proposal that only
names the family of the stored subtype (`ETF` against `ETF_STOCK` — Borsa Italiana says `ETF` for all of ETFplus)
counts as agreement, not as a difference (`isFamilyOnlyProposal`); a refinement (`ETF` → `ETF_STOCK`) is still
offered. When the identifier chooser and the metadata comparison would ask the same question, the comparison waits
while the chooser is open, drops the row the chooser answered, and does not open at all if nothing is left
(`decideComparison`, `components/assets/providerComparisonQueue.ts`).

## Gates

- `frontend/src/lib/utils/__tests__/assetTypeTables.test.ts` reads the Python enum and requires, for every value, an
  icon whose PNG exists, a badge colour, a row in every type filter and in the creation menu (and nothing else),
  families contiguous with their container first, a pastille for subtypes only, badges coloured by content.
- `backend/test_scripts/test_services/test_risk_scenario_catalog.py` checks both directions: every asset type has a
  bucket in every asset-class scenario, and every bucket key is a valid asset type — a type missing from a scenario
  would be shocked by zero **silently**.

## Residuals

K-21, K-22 (AssetModal: reuse prompt over the provider comparison, a wasted catalogue read), K-23 (after Esc in
`TreeSelect` the focus falls on `<body>`), K-16 (Borsa Italiana maps ETC/ETN to plain `ETF` although
`ETF_COMMODITY` exists). Kept on purpose: arrows wrap and Space types into the search of `TreeSelect`.
