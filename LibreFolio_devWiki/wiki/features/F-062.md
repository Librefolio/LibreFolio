# F-062 — Docker Single-Image Deploy

## What it does
LibreFolio deploys as a single Docker image. The Python/FastAPI backend serves the pre-built SvelteKit frontend as static files and the MkDocs documentation site. The image is built on the host after running `./dev.py front build` and `./dev.py mkdocs build`, then `docker build -t librefolio .`.

`docker-compose.yml` provides a one-command deployment (`docker compose up -d`) with a bind-mount for persistent data at `./LibreFolio-data`.

## Layer breakdown
**Infra**: `Dockerfile` (Python 3.13-slim base, installs Python deps, copies backend + pre-built frontend/docs), `docker-compose.yml` (single service, port mapping, data volume, env_file)

## Implementation notes
- Base image: `python:3.13-slim`; system deps: `gcc libffi-dev git` (git needed for justetf pip dep)
- Build sequence: `./dev.py docker build` (calls front build + mkdocs build + docker build)
- Frontend served as static files from `frontend/build/` via FastAPI `StaticFiles`
- Docs served from `mkdocs_src/site/`
- Data dir inside container: `/app/backend/data/prod-docker` (bind-mounted to `./LibreFolio-data`)
- Ports: 6040 (prod), 6041 (test server, for `docker exec --test`)
- Health check: `GET /api/v1/system/health` every 30s, on `localhost:6040` — inside the container uvicorn always listens on 6040 and `PORT` is only the host side of the mapping (until 2026-10-08 the probe used `${PORT}` and a container started with `-e PORT` without compose showed as unhealthy)
- `dev.py` works inside the image for the commands the image can run (`user *`, `info`, `db current|check`); the others say "not available in this installation" — [[problems/devpy-unusable-in-docker-image]]
- HTML entry points are served with `Cache-Control: no-cache, must-revalidate`, hashed `/_app` chunks as immutable — [[problems/stale-frontend-after-update-html-cached]]
- `PORTFOLIO_BASE_CURRENCY`, `LOG_LEVEL`, `PORT` configurable via `.env`
- Two published variants: **full** (`X.Y.Z`, with the documentation screenshots) and **light** (`X.Y.Z-light` and
  `latest`, the screenshots loaded from the online docs site) — [[decisions/release-image-tags-latest-light]]
- The Dockerfile's `frontend` stage refuses a debug or coverage build (`scripts/docker/check_frontend_build.sh`), after
  the 1.1 images shipped a debug frontend and a full image identical to the light one —
  [[problems/release-images-shipped-debug-frontend]]
- Responses are gzip-compressed by the app itself (`GZipMiddleware`, level 6, above 1 KiB) —
  [[decisions/http-gzip-in-the-app]]
- A `VERSION` file left in a checkout after a local image build freezes the version reported from source (R2, open):
  [[problems/stale-version-file-shadows-git-describe]]
- The full image's documentation works offline, formulas included, since `8d47c28c0` (2026-10-12): before, every
  nested page loaded MathJax from jsDelivr — [[problems/docs-mathjax-looked-in-the-page-folder]]
- The image weighed about 2 GB before 1.1.0 (beta feedback F13): a recursive `chown` duplicated every file into a new
  layer, the build toolchain (`gcc`, `libffi-dev`, `git`) sat in the final image, and `.dockerignore` let in
  `backend/data/` — local databases and uploads, a data-leak risk in a published image — and `backend/test_scripts/`.
  Since `f32e460ca` (2026-09-01) every `COPY` into `/app` carries `--chown`, the toolchain lives only in the
  `pybuilder` stage, and both folders are excluded from the build context.
