# F-090 — AssetEvent → Transaction Link (Enrichment)

## What it does
An enrichment layer on top of [[F-051]] (Transaction ↔ AssetEvent Link). While F-051 adds the FK column, F-090 adds the full UX and business logic: when a provider change is detected (e.g., Yahoo Finance dividend event vs existing INTEREST transaction), show a modal to link or unlink the transaction from the event. A linked event is protected from deletion: the
database refuses it (`RESTRICT`), the bulk delete reports it event by event, and since 1.3 the data editor's save is
refused whole (see «Delivered under F-051»).

## Note on relation to F-051
F-051 provides the FK infrastructure. F-090 was planned as the enrichment workflow on top of it: a provider-change
modal, a guard on deleting a linked event, and a linking UI. They were kept separate because F-051 could ship without
the full enrichment UX. *Checked on 2026-10-12 (C-64)*: the guard and the linking UI were delivered under F-051; the
provider-change modal and the reverse lookup were not. The reverse lookup followed on 2026-10-15 (C-65b).

## Implementation notes
- `asset_event_id FK` on `Transaction` (from F-051)
- Delete protection, as built:
  - `RESTRICT` on the FK;
  - a bulk `DELETE` that always answers 200 with one outcome per event, never 409;
  - since 1.3, the editor's save, where an event in use refuses the whole request with 409 `EVENT_IN_USE` (below).
- Provider change modal: shows old event → new event diff, proposes re-link — *not built* (C-65a)
- `GET /transactions?asset_event_id={id}` for reverse lookup — built on 2026-10-15 (C-65b, `5e96df752`), within the
  brokers the user can view
- HIGH priority for Phase 7

## Delivered under F-051 (checked on 2026-10-12, C-64)
- The FK `Transaction.asset_event_id` has `ondelete="RESTRICT"` (`backend/app/db/models.py:830`): an event that a
  transaction references cannot be deleted.
- `DELETE /api/v1/assets/events?asset_id=…&ids=…` (`delete_events_bulk`, `backend/app/api/v1/assets/events.py`)
  answers 200 with one outcome per id:
  - `deleted`;
  - `not_found`, which since 1.3 includes an id of another asset: `asset_id` is required (decision 21);
  - `in_use`, with the linked transactions the user can access (`accessible_transactions`) and a count of the others
    (`hidden_transactions_count`).

  The deletions that succeed are committed even when others are blocked. Since 1.3 the app no longer calls it.
- Since 1.3 the data editor deletes through `delete_ids` of `POST /api/v1/assets/events`, inside its one save, all or
  nothing. Any event of the asset can be deleted there, manual or from a provider. An event in use refuses the whole
  save with 409 `EVENT_IN_USE`, naming the event and the number of linked transactions, without their ids
  ([[decisions/asset-event-saves-all-or-nothing]]).
- A transaction links and unlinks through its own API: `asset_event_id` `0` unlinks and `n > 0` links, under rule 9
  (an event-compatible type, with its asset) — `backend/app/schemas/transactions/transactions.py`.
- The form has the event picker (`AssetEventPicker`, `39005e8ac`).
- The reverse view of a link: `GET /api/v1/transactions?asset_event_id=` lists the transactions linked to an event,
  within the brokers the user can view (C-65b, 2026-10-15, lot I1 of workstream W, `5e96df752`).
