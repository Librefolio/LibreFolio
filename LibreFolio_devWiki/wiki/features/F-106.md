# F-106 — Tool platform

## What it does
A **Tool** is a standalone calculation behind a typed, versioned contract: the caller sends a complete scenario,
the backend computes it in a process of its own and returns a typed result or a structured error. Users open
**Tools** from the sidebar: a hub of cards (`/tools`), one per service the backend publishes, and
`/tools/<tool_code>` for an open Tool. A Tool never changes the portfolio — it records no transaction, places no
order and saves nothing. The platform is labelled experimental; today its catalogue holds one Tool, the PAC
allocator.

Domain: [[domains/infrastructure]].

## Layer breakdown
**Backend**:
- `backend/app/services/tools/` — `base.py` (`ToolPlugin` with the package-wide `contract_version` and
  `implementation_version` and one to sixteen `ToolService`s; `ToolExecutionContext` with `checkpoint()` and
  `claim_engine_window()`), `registry.py` (`ToolPluginRegistry` on the shared `AbstractPluginRegistry`, discovery
  folder `tool_plugins/`), `schema.py` and `schema_export.py` (schemas and fingerprints from the Pydantic adapters,
  a build-only manifest), `catalog.py` (`effective_operation()` clamps every operation to the platform),
  `wire.py` (bounded, Unicode-safe JSON) and the isolated execution: `executor.py`, `worker.py`, `process_tree.py`,
  `resources.py`.
- `backend/app/api/v1/tools.py` — `GET /api/v1/tools/catalog`, `POST /api/v1/tools/compute` (one to four items, of
  any Tool, in one batch) and `GET /api/v1/tools/diagnostics`, all behind `get_current_user`.
- `backend/app/schemas/tools.py` — the transport DTOs and `ToolPlatformPolicy`.

**Frontend**: `frontend/src/lib/features/tools/` — `ToolsHub.svelte` and `ToolHost.svelte`, the client
(`client.ts`), the compatibility check and run preparation (`contracts.ts`), the compiled renderer registry
(`registry.ts`, `defineToolRenderer`), `presentation.ts`, the panels of Settings → About → Plugin diagnostics
(`ToolAboutPanel.svelte`, `ToolDiagnosticsPanel.svelte`) and `components/ToolExecutionMetrics.svelte`. The strict
Zod codecs and the contract map are generated by `frontend/scripts/generate-tools-client.mjs` during
`./dev.py api sync`, and are git-ignored.

## Dependencies
- [[F-059]] Provider registry — `ToolPluginRegistry` extends `AbstractPluginRegistry` and registers with
  `register_plugin`, then adds transactional discovery and quarantine.
- [[F-001]] Authentication — every Tool route depends on `get_current_user`; a disabled account gets 401.
- [[F-066]] Zodios API client — the Tool codecs are a second generation beside the OpenAPI client, run by the same
  `./dev.py api sync`.
- [[F-069]] MkDocs — every service declares a documentation path, which `DocsLink` opens in the current language.

## Enables
- [[F-107]] PAC allocator, the first packaged Tool (`backend/app/services/tool_plugins/pac_allocator.py`, renderer
  `PacPlannerTool.svelte`); its solver budget is the first claim of the engine window
  ([[problems/pac-solver-ran-on-default-budget]]).

## Implementation notes
- The three platform decisions: [[decisions/tool-calculation-without-authority]],
  [[decisions/tool-item-runs-in-owned-process]], [[decisions/tool-contract-from-pydantic-compiled-renderer]].
- **Budgets** — the `ToolPlatformPolicy` defaults since the capacity round of 2026-09-16 (`4a38b9061`): one to four
  items per batch; two worker lanes and eight pending items per API process; one batch and four items per user;
  engine 30 s, soft 44 s, hard 45 s including the process start, cleanup 5 s, request 59 s, client 65 s; 1 GiB of
  memory per job. They hold per API process, not per deployment, and they are limits, not measured throughput.
- **Traps for a new operation** (dossier §2.7.3, still true at `8abce8e87`): a budget the operation omits takes the
  model's default (4 s engine and soft, 5 s hard), so `claim_engine_window()` fails at once with any reserve; one
  invalid operation policy removes the whole service from the catalogue; the PAC `plan` operation's server bound
  equals its request deadline, 59 s, with no slack.
- **Unavailable, with a reason** — a descriptor that cannot run is shown with one of `tool_not_installed`,
  `tool_unavailable`, `contract_not_compiled`, `schema_mismatch`, `ui_mismatch`, `operation_mismatch`,
  `renderer_missing`, `renderer_registration_invalid` or `renderer_collision`; the hub counts them and points to
  Settings → About → Plugin diagnostics.
- **Versions on screen**: `Backend/API <contract_version> · UI <ui.version>`. `implementation_version` is pinned in
  every request and checked on every result, but never displayed.

## Dead ends / Ideas explored
- **Schema, prefill, jobs and cancel endpoints, an MCP server** — out of this increment by the developer's decision
  (plan §1). The developer later called an MCP server «prematuro oltre ogni misura» (2026-10-05, PAC Round 5 §4).
- **A warm worker pool** — rejected: a fresh process per item, atomicity before latency (dossier §1).
- **A demo plugin** — none: the renderer registry shipped empty until the real PAC renderer arrived (`0210f9848`,
  2026-09-25).
- **The first PAC pilot**, P1 `analyze`, published two services from one plugin (`pac_allocator` and
  `portfolio_rebalancer`); it was removed on 2026-09-21 (`b82e59ffa`, «drop P1 prototype, wire planner v2»). The
  catalogue has had one service since ([[decisions/pac-p1-prototype-removed]]).

## Still open
Checked on the code at `8abce8e87`:
- The memory enforcement mode (`capabilities.memory.mode` in the diagnostics, `resources.memory` per job) is in the
  API, but no screen shows it: `ToolDiagnosticsPanel.svelte` and `ToolExecutionMetrics.svelte` render no memory
  field. The dossier of 2026-09-11 called it «the most important line» (§5.1).
- The client waits the platform's `client_timeout_ms` (65 s), not the operation's (`contracts.ts`, `prepareToolRun`;
  dossier §5.4). The PAC declares the same value, so nothing differs today.
- In the observed mode, the summed resident memory of a process tree can count shared pages twice, and a spike
  between two samples can pass unseen (dossier §5.2). The cgroup path was never tested on a real delegated host, and
  no benchmark was run (dossier §6).
