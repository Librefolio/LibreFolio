    🔐 Broker Access Control (RBAC)

    LibreFolio implements a granular Role-Based Access Control (RBAC) system for Brokers. This allows users to share access to their brokerage accounts with other users (e.g., family members, accountants) while maintaining control over permissions.

    📖 Overview

    Access is managed via the BrokerUserAccess table, which links a User to a Broker with a specific UserRole.

    erDiagram
    USER ||--o{ BROKER_USER_ACCESS : "has access"
    BROKER ||--o{ BROKER_USER_ACCESS : "granted to"

    BROKER_USER_ACCESS {
        int user_id FK
        int broker_id FK
        enum role "OWNER, EDITOR, VIEWER"
        decimal share_percentage "0..1, OWNER-only, scales aggregation"
    }

    🛡️ Roles and Permissions

    There are three roles with increasing levels of privilege:

    Feature VIEWER EDITOR OWNER
    View Broker Details ✅ ✅ ✅
    View Transactions ✅ ✅ ✅
    View Reports/Charts ✅ ✅ ✅
    View Report Files (BRIM) ✅ ✅ ✅
    Add/Edit Transactions ❌ ✅ ✅
    Upload/Parse/Delete Files (BRIM) ❌ ✅ ✅
    Edit Broker Settings ❌ ✅ ✅
    Manage Access (Add/Remove Users) ❌ ❌ ✅
    Delete Broker ❌ ❌ ✅

    For BRIM report files the administrator (is_superuser) needs no role, a file with no broker is its uploader's and the administrator's only, and a parse also needs EDITOR or OWNER on the broker it imports into: see Who reaches a report file.

    📋 Role Definitions

    1. 👁️ VIEWER: Read-only access. Ideal for sharing portfolio visibility without risk of data modification.
    2. ✏️ EDITOR: Operational access. Can manage the day-to-day data (transactions, imports) and broker settings (name, icon), but cannot perform destructive administrative actions (deleting the broker) or change who has access.
    3. 👑 OWNER: Administrative access. Full control over the broker.

    📏 Key Rules & Constraints

    📊 Ownership share (share_percentage)

    Each access row carries a share_percentage (0.000000–1.000000) used only for portfolio aggregation, never for permissions:

    • OWNER: the broker's creator gets 1.00; through PUT /api/v1/brokers/{broker_id}/access, every OWNER gets the share its item carries — 0 when the item has none, even for an OWNER already on the broker. The share may be reduced for co-ownership (e.g. joint accounts); EDITOR and VIEWER default to 0.00 (delegated operator, read-only accountant).
    • The sum of shares across a broker's users must not exceed 1.00 (validated on add/update); it can be less (a co-owner may simply not be in the system).
    • 0 % is a valid share: a 0 % OWNER keeps full admin rights but contributes nothing to the owner's aggregated numbers.
    • Aggregation scales by share only for OWNERs — EDITOR/VIEWER rows always carry share 0 by schema rule yet see full data, so the engine uses scale 1 for them (effective_share() in financial_math/native_cash.py, through broker_shares(), called by portfolio_service.py and financial_math/portfolio/engine.py). Role/share edits change every scaled number but not the underlying data, so they also join the cache fingerprint for instant invalidation.
    • apply_ownership_share=False on the report and the positions series (for the broker page) skips the scaling: every broker counts whole, as an EDITOR sees it, whatever the role and the share (native_cash.broker_shares(), the whole broker).

    🔒 The "Last Owner" Rule

    To prevent brokers from becoming "orphaned" (left without an OWNER to manage their access or delete them), the system enforces a strict rule:

    A broker always keeps at least one OWNER. The last OWNER cannot be removed or downgraded — by anyone, themselves included — but can leave, and leaving deletes the broker.

    If a broker has only one user with the OWNER role:

    • ❌ Nobody — neither that user nor the administrator — can remove them or change their role to EDITOR or VIEWER without making another user OWNER: PUT /api/v1/brokers/{broker_id}/access (bulk_update_access()) refuses any configuration without an OWNER (400, "At least one OWNER is required").
    • ❌ That user cannot demote themselves with PATCH /api/v1/brokers/{broker_id}/access/me (update_own_role()): 400, "The last OWNER cannot demote themselves — promote another user first".
    • ⚠️ That user can leave with DELETE /api/v1/brokers/{broker_id}/access/me (leave_broker()), and leaving deletes the broker with its transactions: see Self-Management.
    • ✅ To leave without deleting the broker, they first make another user OWNER with the PUT; they can then leave, or drop their own row in that same PUT.

    🔧 Self-Management

    • 🚪 Leaving: any user can remove themselves from a broker at any time (leave_broker). EDITOR/VIEWER always succeed. An OWNER may leave when at least one other OWNER remains — otherwise leaving as the last OWNER deletes the broker entirely. Its transactions do not go by a database cascade: delete_by_broker() deletes them, and the other half of a pair held on another broker stays there without its link — as the standalone row a split of the pair leaves or, for the giving leg of a TRANSFER whose cost needs a missing conversion, still a TRANSFER (see Broker Deletion). BRIM report files are cleaned up by the API layer.
    • ⬇️ Self-demotion (update_own_role): EDITOR → VIEWER is always allowed; OWNER → EDITOR/VIEWER is allowed only when another OWNER remains, and demoting from OWNER zeroes the share (only OWNERs may hold share > 0). Promotions go through the PUT, OWNER or administrator only.
    • 🗑️ Deleting an account applies leave_broker() to every broker of the account, in one commit: see Deleting an Account.

    🔧 Implementation Details

    The logic is centralized in backend/app/services/brokers/access.py (BrokerAccessMixin, part of BrokerService).

    • 🔍 _check_user_access(broker_id, user_id, min_role): Core internal method to verify permissions.
    • 📋 list_accesses(): The users with access to a broker, with role and share.
    • 🔄 bulk_update_access(): Replaces a broker's whole access configuration in one step (OWNER or administrator): adds, role changes and removals; at least one OWNER must remain, and the shares add up to at most 100 %.
    • 🚪 leave_broker() / update_own_role(): The self-service paths described above.

    🌐 API Endpoints

    Access management is exposed via the following endpoints (backend/app/api/v1/brokers.py):

    • GET /api/v1/brokers/{broker_id}/access: the users with access, with role and share (list_accesses()). Any authenticated user can read the list of any existing broker, email addresses included; 404 only when the broker does not exist.
    • PUT /api/v1/brokers/{broker_id}/access: replaces the whole access configuration in one step (bulk_update_access()). The body is the complete desired list of {user_id, role, share_percentage}: users missing from it lose their access, new ones are added, roles and shares are updated, in one transaction. Granting, changing and revoking access all go through it. OWNER or administrator only (403 otherwise); 400 when a rule fails (no OWNER, shares adding up to more than 1.0, a duplicate or unknown user); 422 for an empty list or a share the schema refuses (outside 0–1, or above 0 for an EDITOR or VIEWER).
    • PATCH /api/v1/brokers/{broker_id}/access/me: self-demotion only (update_own_role()), body {role}; 400 for any other change and for the last OWNER's demotion, 403 without access to the broker.
    • DELETE /api/v1/brokers/{broker_id}/access/me: leave the broker (leave_broker()); the response's broker_deleted is true when the last OWNER's leaving deleted it. 403 without access to the broker.

    👑 Superusers and the User CLI

    Besides the broker roles, every account carries one system-wide flag, users.is_superuser: the administrator of the admin manual. It belongs to the account, not to a broker.

    • Granted to the first account registered (POST /api/v1/auth/register while first_account_open() holds, that is while count_users() is 0, inactive accounts counted: accepted whatever the registration mode, and an administrator even when the invitation it spends grants a regular account), to an account registered with an invitation that grants it (grants_admin, see Invitations), to an account created with ./dev.py user create without --role user (--role admin is the default: scripts/user_cli.py maps it to its internal create-superuser command, which calls user_service.create_user() with is_superuser=True), by ./dev.py user promote, and by PATCH /api/v1/users/{user_id} with is_superuser: true. ./dev.py user create … --role user maps to the internal create-user command instead (is_superuser=False): a regular account, even as the first account of an empty database. The administrator of LIBREFOLIO_ADMIN_EMAIL is a superuser from its creation by the startup, inactive until its setup link is spent (The Initial Administrator).
    • Promote and demote go through user_service.set_user_admin() from the CLI, which refuses a no-op (already an admin, not an admin), the demotion of the last active administrator and, since lot A-43, the demotion of the initial administrator waiting for its setup, and through user_service.update_user_status() from the administrator API, whose route refuses that demotion first (409 PENDING_SETUP). A demotion also ends every session of the account (user_service.end_sessions() raises users.session_version, see Session Revocation); a promotion does not. Self-deletion has the same guard: DELETE /api/v1/auth/users/me answers 400 to an administrator when no other active administrator remains (count_active_superusers(), counted under the write lock since lot A-52: see Decided under the write lock), with detail {"error_code": "LAST_ADMIN", "message": "Cannot delete account: you are the last active administrator"} since lot A-16 (a bare sentence before); the deletion dialog words it with its own key (Account Errors). The administrator API deletes no administrator, active or not: DELETE /api/v1/users/{user_id} answers 409 DEMOTE_FIRST until the account is demoted (Deleting an Account), except for the initial administrator waiting for its setup, which cannot be demoted and is deleted directly.
    • Stale reads (lot A-51): set_user_active() (user deactivate, user activate), set_user_admin() (user promote, user demote) and update_user_status() (the administrator API) read the account again under SQLite's write lock before they decide (refreshed_under_lock(), see Decided under the write lock): the last-administrator guard, then «waiting», which set_user_admin() reads to refuse a demotion, and set_user_active() and update_user_status() to tell a cancellation from a deactivation (A setup completed meanwhile). The account they first read may be stale: on a new instance whose only account is the initial administrator waiting for its setup, the setup can complete in the same millisecond as the command. Read stale, user demote used to remove the only administrator, and user deactivate to answer success and end the new owner's sessions without deactivating it, since the column it set was equal to the stale value. Both now refuse it as the last active administrator, nothing changed.
    • Applied at the next request: the user CLI writes the database directly, with the server running or not, and get_current_user() reloads the user on every request. A deactivated account (user deactivate, user_service.set_user_active(), or the administrator API) gets 401 User account is disabled; its login, with the right password, gets 403 ACCOUNT_DISABLED — or 403 EMAIL_NOT_VERIFIED while it waits for its email verification. Deactivation refuses the last active administrator, and ends every session of the account: user activate lets the user sign in again, but brings none of the old sessions back.
    • Password reset (user reset, user_service.reset_password()) sets the new hash, computed in a worker thread off the event loop, and ends every session of the account in the same commit: each device gets 401 at its next request, and signs in again with the new password. The same commit revokes the account's live password-reset links (A-27) and retires its setup links (A-32, The Initial Administrator). A password-reset link does the same when it is spent. To keep the account out altogether, deactivate it.
    • The account's own changes end its other sessions as well: a password change (POST /api/v1/auth/change-password) and an email change (PUT /api/v1/auth/profile, which asks for the current password: see Changing the Email). The device that made the change gets a new cookie and stays signed in; a username change ends no session. Every change that ends sessions is in Session Revocation.
    • A new address revokes the account's live email_change links together with its password-reset and setup links (user_service.update_profile, A5-4): a change of address asked for before cannot move it again. On a managed instance, ./dev.py user reassign-owner <username> (cmd_reassign_owner) takes an account back to the address of LIBREFOLIO_ADMIN_EMAIL: it runs instance_owner.assign_owner_and_send_reset, the treatment of a restore (unusable password, sessions ended, links neutralised, one reset link), and refuses on a non-managed profile.
    • Password rules: create and reset call validate_password() in scripts/user_cli.py, a thin wrapper over password_policy.failed_rules(): the same rules as the API and the app (Password Rules), checked before anything is read from the database. Each rule missed prints a line that starts with its code, such as digit: the password must contain a digit, and the command exits with 1.
    • Usernames and addresses (lot A-21a): create refuses a username holding @ and, since lot A-46, one outside 3 to 50 characters, as registration and the Profile do; create and set-email refuse an address that is another account's username, in any A–Z case: through user_service.create_user() and user_service.update_profile(). The command prints the service's message after ❌ — A username cannot contain @: the sign-in reads it as an email address, A username must be 3 to 50 characters long, or Email already registered — and exits with 1, writing nothing. The service's refusal is an AccountError, a str that also carries a code (lot A-47), which the API reads instead of the message. See Which Account an Identifier Names.

    The admin commands are in Command-Line Tools.

    🚪 Registration, Invitations and the Admin API

    Who may create an account, how many accounts an instance may hold, and what an administrator can do to the other accounts. The rules are in backend/app/services/accounts/registration_service.py, the account changes in user_service.py, and the variables in backend/app/config/accounts.py (administrator side: Configuration, section «Accounts and Sign-ups»). The administrator an operator creates from the environment has its own section: The Initial Administrator.

    🎚️ Registration Modes

    effective_registration_mode(session) returns a RegistrationModeState(mode, locked): LIBREFOLIO_REGISTRATION when it is set (blank counts as unset; case and surrounding spaces are ignored), with locked=True; otherwise the global setting registration_mode (Settings System), with locked=False.

    The default of that setting is invite (decision 36), and it has one source: GLOBAL_SETTINGS_DEFAULTS in backend/app/schemas/settings.py. The startup seeding writes it on a new install, and get_setting_value() answers it while the row is missing: the service passes no fallback of its own. The seeding creates only missing rows, so an existing install keeps its row, whatever its value. An install that holds accounts but no row has run with the earlier default, open: step 5 of migration 005_release_1_3_0_schema writes that open row before the seeding runs (GLOBAL_SETTING), so an upgrade never closes registration in silence.

    Mode POST /api/v1/auth/register accepts
    open Anyone. An invite_token is optional, but must be a valid invitation when given, and then sets the role
    invite Only a valid invitation
    disabled Nobody, invitations included

    Both sources fail closed. A LIBREFOLIO_REGISTRATION that is not a mode makes the mode disabled, and still locks the setting: registration_mode_pinned() only asks whether the variable is set. A stored value that is not a mode also reads as disabled. Either is logged by _report_invalid() as the error event Invalid account configuration, with two fields: problem, the variable or the row and its value, and consequence, registration stays closed until it is fixed. The function is a functools.cache, so each problem is logged once per process. The startup configuration checks do not cover these variables.

    register_user() holds the rule of POST /api/v1/auth/register (AuthRegisterRequest, with an optional invite_token) and owns its transaction. The route checks the password before calling it, so PASSWORD_TOO_WEAK comes first:

    Situation Outcome
    A password that misses a password rule 400 PASSWORD_TOO_WEAK, with rules, the codes missed. Checked by the route before anything else — the mode, the invitation, the limit, a taken username or email — the first account included. Nothing is written, and an invitation given with it stays unspent
    No account at all (first_account_open(): count_users() is 0, an inactive account counts) Created as an administrator, whatever the mode, the limit and the role of an invitation. Without an invite_token, nothing else is checked. With one, the invitation must be valid — otherwise 400 INVITE_INVALID, and the instance stays empty — and the registration spends it as any other does (row A valid invitation): its link then reads consumed
    Mode disabled 403 REGISTRATION_DISABLED
    Mode invite, no invite_token 403 INVITE_REQUIRED
    A token that is not a valid invitation: unknown, of another purpose, expired, used or revoked 400 INVITE_INVALID
    A valid invitation Created in the invitation's role (grants_admin; the first account is an administrator whatever it says). The account and the consumption of the invitation (consumed_by_user_id) are committed together. The limit is not checked: the invitation already holds its place
    Mode open, no invite_token Created as a regular account, within the user limit
    require_email_verification on, any account but the first Created inactive, with a verification token that holds its place; the answer says verification_required: true and verification_email: "sending", and the email goes after it — unless the client address already had the emails of LIBREFOLIO_SIGNUP_EMAILS_PER_ADDRESS registrations in the hour (20 by default): the answer then says verification_email: "held", the account waits without its email, and its owner, told so by the sign-in, asks for the link again from there. "sending" means queued, not delivered; verification_email is null without verification. With no email with a link able to go out, 409 EMAIL_VERIFICATION_UNAVAILABLE, and nothing is created: an invitation stays unspent. See Email Verification

    ✉️ Invitations

    An invitation is an invite account token: 7 days, single use, link /invite#token=…, and no user_id, as its account does not exist yet.

    • Created by create_invite(), from POST /api/v1/users/invites or ./dev.py user invite, with grants_admin, email and created_by_user_id (NULL from the command line). It refuses in mode disabled (REGISTRATION_DISABLED), and when the instance is full (USER_LIMIT_REACHED) unless called with enforce_limit=False, as only the command line does. It flushes and does not commit.
    • The email is a suggestion, not a constraint. It records whom the invitation is for, and POST /api/v1/auth/tokens/inspect returns it to whoever holds the token, but registration never compares it with the address of the new account: the developer rejected D-A16, the proposal to bind the two.
    • Listed by list_pending_invites(): the live ones (not consumed, not revoked, not expired), oldest first. Revoked by revoke_invite(invite_id), which returns False for anything that is not a live invitation; it flushes and does not commit.
    • Spent only by register_user(), as above.

    POST /api/v1/auth/tokens/inspect {token, purpose}, with purpose invite, password_reset or admin_setup (The Initial Administrator), is public and writes nothing. It answers {status, purpose}, the status being valid, expired, consumed, revoked or unknown (also for a token of another purpose).     📏 The User Limit

    LIBREFOLIO_MAX_USERS (unset or blank: no limit) bounds the places counted by user_usage(): the active accounts (users.is_active), the live invitations, and the inactive accounts that wait: those holding a live email-verification token (Email Verification) and the administrator waiting for its setup (The Initial Administrator), each account counted once. A deactivated or deleted account frees its place; an invitation holds one from its creation until it is revoked or expires, and hands it to the account it opens; an account waiting for its email verification holds one while its link is live. A value that is not a whole number of at least 1 makes max_users() raise ValueError, and log_configuration_audit() calls it, so the start stops with an error that names the variable (CL-1). The registration check _max_users() still reads such a value as a limit of 0, logged like an invalid mode, for a process the audit does not guard; GET /panel/status answers users_limit: null for it, never a 500.

    🗑️ Deleting an Account

    DELETE /api/v1/users/{user_id} deletes another account by the rule of deleting one's own: broker by broker, the last-owner rule of BrokerService.leave_broker(). A broker the account is the only OWNER of goes, with its transactions and its report files; on the others only the account's access goes. An inactive co-owner's OWNER row counts as another owner. The rule, the shared helper and the preview are in Deleting an Account.

    GET /api/v1/users/{user_id}/deletion-preview tells the administrator beforehand what the deletion would take, by the same rule, writing nothing: brokers_deleted, brokers_left and transfers_unpaired. GET /api/v1/auth/users/me/deletion-preview gives any signed-in user the same for their own account.

    After require_admin, the deletion refuses, in this order:

    1. 404 User not found: no such account;
    2. 409 SELF_DELETION: the caller's own account, which is deleted from the profile (DELETE /api/v1/auth/users/me);
    3. 409 ACCOUNT_PROTECTED, with the reason of the protection hook. It comes before DEMOTE_FIRST because demoting a protected account is refused too;
    4. 409 DEMOTE_FIRST: an administrator, active or not. It must be demoted first, so the last administrator can never be deleted from here. Not the initial administrator waiting for its setup (is_pending_admin(), lot A-43): it cannot be demoted (409 PENDING_SETUP) and never was an active administrator, so it is deleted directly, the hard cancellation of its setup: its setup links go with it (account_tokens.user_id cascades), its place is freed, and nobody waits any more: ./dev.py user setup-link finds nobody, and a next start with the variables still set answers ignored, since the instance has accounts (The Initial Administrator). Whether the account is an administrator, and whether it still waits, is read under SQLite's write lock, on the account read again (Decided under the write lock): one set up (lot A-51) or promoted (lot A-55) since the route's first read answers DEMOTE_FIRST, rolled back, nothing deleted; one deleted meanwhile answers the 404 of point 1 (lot A-54).

    Each 409 carries detail {error_code, message}, plus reason for ACCOUNT_PROTECTED. Otherwise the route calls user_service.delete_account(), the helper of DELETE /auth/users/me too, and answers 204 with an empty body. All or nothing: a technical failure rolls everything back and answers 500 Account deletion failed: nothing was deleted. The deleted account's sessions get 401 at their next request.

    • Log: one structured event, Account deleted by an administrator, with user_id, username, admin_id, brokers_deleted (the ids of the deleted brokers) and files_removed. A failure logs Account deletion by an administrator failed: nothing was deleted, with user_id, admin_id and the traceback.
    • Blocked instance: both previews and the administrator's deletion are outside ALLOWED_WHEN_BLOCKED (Instance Block): 423 for a signed-in caller, 401 for anyone else. Of the deletion routes, only DELETE /api/v1/auth/users/me is on the list.

    🛡️ Protected Accounts

    user_service.account_protection(user) -> Optional[str] gives the reason why nobody may delete, deactivate or demote an account, or None. It is the hook for the owner of a managed instance, the administrator who pays for it (PAYING_ADMINISTRATOR). On any other profile it returns None for every account. On a managed instance (LIBREFOLIO_PROFILE=managed):

    • the account recorded as the instance owner (users.is_instance_owner) is protected by that mark alone, whatever its address and whatever the variable says;
    • once the startup step owner-sync has read the owner (user_service.note_recorded_owner()), the mark decides alone when an owner is recorded: an account that holds the address of a variable changed in conflict is a stranger and never receives the owner's protection;
    • when the step recorded nobody, the account with the address of LIBREFOLIO_ADMIN_EMAIL (A–Z case aside) is protected by its address only while it is an active administrator (the criterion by which the step records an owner);

    • before the step has run (a command, a test) the A5-1 address rule is the fallback: the address alone protects.

    • GET /users reflects it in protected (AdminUserRead), as do the accounts PATCH returns.

    • DELETE /users/{user_id}, and a PATCH /users/{user_id} that deactivates or demotes the account, or cancels the setup link of the initial administrator waiting for its setup (is_active: false on that inactive account, lot A-43, The Initial Administrator), answer 409 ACCOUNT_PROTECTED with that reason. The PATCH checks it first, before PENDING_SETUP, the user limit and the last-administrator rule.
    • Promoting or reactivating a protected account is not refused.
    • The command line stays above protection: ./dev.py user deactivate, user demote and the other user commands never read the hook, as the operator of the server may do what the administrator API refuses.

    📬 The Owner's Address

    🔑 Password-Reset Links

    A reset link is a password_reset account token: 30 minutes, single use, link /reset-password#token=…, bound to its account (user_id). Unlike ./dev.py user reset, the administrator does not choose the new password: whoever spends the link does.

    • Issued by user_service.create_password_reset(), from POST /api/v1/users/{user_id}/password-reset-link or ./dev.py user reset-link <username>, and, when email works, from Forgot Password? on the login page (POST /api/v1/email/password-reset, workstream E): that link is never shown, only emailed to the account's own address, within its limits, and never while an administrator's reset link is still live (A Forgotten Password). It first revokes the account's live reset links, so only the newest one works. Issuing a link ends no session.
    • Spent by POST /api/v1/auth/password-reset {token, new_password}, which is public. new_password must meet the password rules, checked before the token is read: a weak one is 400 PASSWORD_TOO_WEAK, and the link is neither spent nor inspected, so a valid link stays valid. complete_password_reset() consumes the token, hashes the new password with bcrypt in a worker thread, ends every session of the account, revokes its other live reset links and retires its setup links (The Initial Administrator), in one commit; the answer is 200. A link that is not valid (used, expired, revoked, unknown or of another purpose) changes nothing: 400 TOKEN_INVALID.
    • Revoked with the account's password or address: a password change, an email change (the same address in another A–Z case is none) and ./dev.py user reset revoke its live reset links, whoever issued them, in the commit of the change (lot A-27, Session Revocation).

    • Registration. The waiting administrator is a users row, so first_account_open() is false from the first start, and nobody registers as the first account: register_user() applies the mode, invite unless LIBREFOLIO_REGISTRATION pins another. The step writes registration_mode only when it creates the administrator.
    • Delivery, only after created with a generated token. deliver_setup_link(result, engine=…) writes the link once in the log, at WARNING: Setup link of the initial administrator, single use: open it to choose the password, with link (public_link(): the full address with LIBREFOLIO_PUBLIC_URL, otherwise the path, and a note asking to put the server's address in front of it) and expires_at. Then, when require_email() and require_links() allow it, it emails the link to the account's address with build_admin_setup() (Email Service), in the instance's language (instance_language()). The startup runs it in a background task (asyncio.create_task()), with a session of its own, so a slow SMTP server never delays the start. It never raises: an email that cannot go logs Setup link of the initial administrator not emailed (INFO), with the exception's class in reason, and the link in the log still works. A token from the variable is neither logged nor emailed: the panel that chose it delivers it.
    • Several workers. Each worker runs the step, and only one creates the administrator. SQLite runs in WAL with a 30 s busy_timeout: a transaction whose first statement writes waits for the write lock, while one that reads first and writes later can fail at once with database is locked if another connection wrote in between. So _create_pending_admin() commits, which ends its reads, and starts with a write, the registration_mode row: it holds the write lock before it counts the accounts. The worker that comes second finds the account, goes on as pending, and delivers nothing. On a restart, a worker that finds the lock taken while another re-arms or renames answers pending, and lets that one apply the change.

    The setup's status, for a hosting panel (lot H-61). admin_setup_status(session, *, now=None) tells the status route of a hosting panel where the setup of the initial administrator stands. It answers an AdminSetupStatus, a frozen dataclass: state, an AdminSetupState (a StrEnum, so it formats and serialises as its value: none, pending, done or expired), and setup_expires_at, in UTC, for pending only, None otherwise. It reads the admin_setup links of every account, though only the F02 administrator ever gets one; the links of the other purposes (invitations, password resets, email verifications) never count. The status is not «waiting» (pending_admin(), above): an administrator whose link ran out or was cancelled still waits, and its setup reads expired. The rule, in this order («done wins»):

    1. No admin_setup link stored: none. None was ever issued, or the account that held them was deleted: account_tokens.user_id is ON DELETE CASCADE, and its links went with it (Deleting an Account).
    2. Any admin_setup link consumed: done. Spent by the setup (complete_admin_setup(), below), or retired because the account was activated or given a password another way (A-32, below). A consumption is final: no link is issued after one (pending_admin() wants none consumed), so a stray newer link, which a setup through an older one leaves revoked, never makes a set-up instance read expired.
    3. Otherwise the latest link, by created_at then id, decides. Revoked without use — the setup cancelled (A-43), the address changed (A-33, above) — or past its expiry (expires_at <= now): expired. Otherwise pending, with that link's expires_at as setup_expires_at. A link replaced by a newer one (issue_setup_link(), a re-arm) is revoked too, but the newer one is then the latest, and decides.

    now, the moment the expiry is compared with, is the clock (utcnow()) when left out. The function only reads: it writes and commits nothing, leaves nothing in the session for its caller to commit, and never takes SQLite's write lock.

    The setup. POST /api/v1/auth/setup {token, new_password} (AdminSetupRequest, token of at most 200 characters) is public:

    1. The password rules come first: 400 PASSWORD_TOO_WEAK with rules, as for registration, a reset and a password change. Nothing is read or written, and a valid link stays valid.
    2. complete_admin_setup(session, token, new_password) spends the token first, with consume_token(), as a reset link does: of two requests racing for one link, only one gets it. A link that is not a live setup link (used, expired, revoked, unknown, of another purpose) changes nothing: 400 TOKEN_INVALID. The link of an account that is already active is refused the same way: the spending is rolled back, and every setup link of the account is retired (token_service.retire_tokens(), lot A7b-2), with the WARNING Setup link refused and retired: the account is already active. Since lot A-42, so is the link of an account another of whose setup links was already consumed (_setup_spent_before()): the setup done through it, or the links retired. That is a link left live by a race with a new link, or by an earlier 1.3 build, and its WARNING reads Setup link refused and retired: the account was set up before. Once the account is set up, by any way, none of its links may set its password, nor make it wait for its setup again once deactivated. Both refusals come before bcrypt (The Setup Link's Lifecycle).
    3. Otherwise, in one commit: the bcrypt hash of the new password, computed in a worker thread; the account active; its sessions ended (end_sessions(): session_version + 1); the link's consumed_by_user_id set to the account; its other setup links revoked.
    4. The answer is the login's: 200 AuthLoginResponse, show_donation_popup and user.whats_new (What's new) included, and the session cookie of _issue_session_cookie(). The administrator is signed in.

    The route is not in ALLOWED_WHEN_BLOCKED (developer's decision P16: a blocked instance stays blocked until the subscription is paid): on a blocked instance it answers 401, like registration, and the link keeps running out its 72 hours. The pinned list of test_instance_block.py refuses any addition.

    POST /api/v1/auth/tokens/inspect takes purpose: "admin_setup": a valid setup link answers username and expires_at, as a reset link does (Invitations).

    The command line. ./dev.py user setup-link, with no argument (cmd_setup_link() in scripts/user_cli.py): issue_setup_link() revokes the waiting administrator's setup links, then, under the write lock that revocation took, reads «waiting» again (lot A-42, The Setup Link's Lifecycle): an account set up in the meantime gets no link. Otherwise it issues a generated one, 72 hours, which the command prints as reset-link prints its link: the full address with LIBREFOLIO_PUBLIC_URL, otherwise the path and a note. It sends no email. Without a waiting administrator, or once it was set up in the meantime, it prints ❌ No administrator account is waiting for its setup link and exits with 1.

    Set up another way (lot A7b-2, A-32). The setup link is not the only way in, and the command line stays permissive on purpose: ./dev.py user activate and ./dev.py user reset on the waiting administrator are how an operator sets it up without its link (activate alone leaves an active account whose password nobody knows, until user reset or a reset link gives it one). Whatever the way, the account's setup links are retired in the transaction of the change, with token_service.retire_tokens(…, purpose=AccountTokenPurpose.ADMIN_SETUP): revoked and consumed at once (Revocation). The callers:

    • an activation: user_service.set_user_active(), behind user activate, and user_service.update_user_status(), behind PATCH /users/{user_id}, which refuses the waiting administrator itself first (409 PENDING_SETUP);
    • a new password: user_service.reset_password() (user reset), user_service.complete_password_reset() (a reset link spent, one an administrator issued for the waiting account included) and POST /auth/change-password;
    • complete_admin_setup(), when it refuses the link of an account already active, or, since lot A-42, of an account another of whose setup links was consumed (above).

    This applies to every account with a setup link, not only the waiting one. Afterwards the old link inspects revoked (the setup page's withdrawn card) and sets nothing (400 TOKEN_INVALID), and the account is out of pending_admin_filter(), inactive or not: pending_setup is false, PATCH /users/{user_id} reactivates it as any inactive account (no 409 PENDING_SETUP), issue_setup_link() returns None (user setup-link prints its error), and the startup answers ignored. A reset link issued and never spent retires nothing: the account keeps waiting, and its link still works. Since lot A-43, a demotion of the waiting administrator is refused, and its deactivation revokes its setup links: the account keeps waiting, but the link handed over stops working (below).

    The user limit. user_usage() counts the waiting administrator (pending_admin_filter()) beside the active accounts and the live invitations, its link live or not: it holds a place from its creation, and keeps it once active. Set up another way but still inactive, it waits no more and holds no place, as any inactive account.

    The administrator API and the Users tab (lot A7b). The account waiting for its setup is marked:

    • GET /users and the answer of PATCH /users/{user_id} carry pending_setup (AdminUserRead, default false), true for an account of pending_admin_filter(): inactive, with at least one admin_setup token and none of them consumed — live, expired or revoked alike, an administrator or not; a retired token is consumed, so an account set up another way is false. registration_service.pending_admin_ids() reads it for the list, is_pending_admin() for one account. An expired link keeps the account waiting, and so does a cancelled one: ./dev.py user setup-link gives it a new one.
    • PATCH /users/{user_id} with is_active: true on that account, alone or with is_superuser, answers 409 with detail: {error_code: "PENDING_SETUP", message} and changes nothing: nobody knows its password, and an activation would retire its setup links (above). The check comes before the user limit. Since lot A-43 a demotion is refused with the same detail, word for word: is_superuser: false, alone or with is_active: false, changes nothing either, checked right after the protection hook. The account keeps its role until its setup: its link is cancelled, or the account deleted, instead (below).
    • The Users tab draws the account with the badge Waiting for setup; Cancel setup link in place of Reactivate, Remove administrator turned off with the reason pending-setup, Delete enabled (on a protected account, all three are off with the reason protected); and a hint that names dev.py user setup-link (UserRow).
    • No route issues a new setup link: in release 1.3 the command line does (backlog).

    Cancelling the setup link (lot A-43). Deactivating the waiting administrator cancels the link handed over: PATCH /users/{user_id} with is_active: false (the Users tab's Cancel setup link, after a confirmation, sends {is_active: false, cancel_setup: true}, lot A-51) and ./dev.py user deactivate <username> revoke its setup links, live or expired (user_service._end_setup_links()). Whoever holds the link can no longer set the account up: inspected, it answers revoked, and POST /auth/setup with it 400 TOKEN_INVALID. The account keeps waiting: pending_setup stays true, in the 200 of the PATCH too, it keeps its place, and its reactivation stays 409 PENDING_SETUP. A new link comes from ./dev.py user setup-link, or from a new LIBREFOLIO_ADMIN_BOOTSTRAP_TOKEN at the next start; the same token re-arms nothing, being stored already, and that start is expired, with the WARNING of a withdrawn link rather than of an expiry (lot A-50: the latest setup link is revoked and never consumed), its remedy unchanged: The initial administrator's setup link was withdrawn (cancelled, or its address changed): …. The cancellation itself logs the WARNING of The Setup Link's Lifecycle; a second PATCH finds no link left to revoke and changes nothing. A protected account refuses it on the API, 409 ACCOUNT_PROTECTED, nothing changed and the link still working: update_account() asks the hook about the cancellation (cancel) as about a deactivation or a demotion. The command line stays above protection. The hard cancellation is the deletion, which needs no demotion first for this account (Deleting an Account). Deactivating any other account retires the setup links it never consumed instead, so that a stray one can never make it wait for its setup.

    A setup completed meanwhile (lot A-51). The Users tab's row can be stale: the administrator may have spent its link since the list was loaded, or in the same millisecond. Sent with {is_active: false} alone, the same body as a deactivation, a cancellation from a row loaded before the setup would have deactivated the new owner. So the tab adds cancel_setup: true, which makes the request the cancellation and nothing else: update_user_status() reads «waiting» under SQLite's write lock, on the account read again, and an account that no longer waits answers 409 SETUP_COMPLETED (This account does not wait for its setup: nothing was changed, a sentence that also fits a direct API call on an account that never waited; the tab, which sends the field only from a waiting row, says the administrator completed its setup in the meantime), rolled back, with the INFO line Setup cancellation refused: the account does not wait for its setup (user_id). The tab reloads, and the row shows the account active. Without the field, {is_active: false} keeps its meaning, a deactivation, decided on the account as the lock finds it: in the same-millisecond race it deactivates the administrator just set up, and its answer is what the database holds (before lot A-51, a 200 read from the stale account, nothing deactivated). The deletion and the command line read the account again under the lock as well (Deleting an Account, Superusers and the User CLI).
