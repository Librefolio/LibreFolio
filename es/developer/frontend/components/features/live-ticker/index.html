    📡 Live Prices

    LibreFolio shows live current prices on the Assets list and on the asset detail page. Both pages poll the bulk current-price endpoint themselves, through one shared helper that pauses while nobody is using the page (Pause and resume) and waits longer after a failed poll or during a provider's pause (Failures and provider pauses); there is no ticker component. The Assets list fetches through a small service, livePriceService; the asset detail page posts its one id itself, through the generated API client, and uses only the service's helpers to read the answer, one answer feeding both its price summary and its chart.

    The page also covers the notice Updating prices…, which the web app shows while the server catches up on prices, through the same helper: see Updating prices….

    No LiveTicker component

    The LiveTicker badge strip this page used to describe was removed in August 2026 (commit cd7b24bb4); the page keeps its address for the existing links. The dashboard shows no live prices: it never calls the endpoint.

    🧩 The shared service

    lib/services/livePriceService.ts holds the helpers both pages share:

    Export Used by Description
    fetchCurrentPrices(ids) Assets list Wraps POST /api/v1/assets/prices/current and returns LivePriceResult[]: {assetId, value, currency, source, error, errorCode, retryAfter}, with value parsed to a number (null when the asset has no price). An empty ids list sends nothing. The endpoint refuses more than 1,000 ids (422 bulk_too_many_items, R13-SEC9-1), so the ids go through sendBulkBatches(ids, () => 0, send) (lib/api/bulkBatches.ts, Z-27; X-R64): consecutive batches of at most 1,000, in the order given, one request after the other, with no day estimate, and the items of every batch mapped in that order, as if one request had answered; up to 1,000 ids it is one request. All or nothing: a failed batch rejects the call with its own error, as axios raised it, so livePollFailure still reads its Retry-After, and nothing is sent after it.
    toLivePriceResult(raw) both pages One item of the answer as a LivePriceResult; fetchCurrentPrices maps every item through it. errorCode is the item's error_code: RATE_LIMITED while the asset's provider is paused. retryAfter is its retry_after, the seconds until that pause ends, null when absent or not a number.
    livePollOutcome(results, now?) both pages The outcome of a poll that got an answer: {ok: true, notBefore} at the end of the shortest pause when every result is RATE_LIMITED with a retryAfter; {ok: false} when every result is RATE_LIMITED and one has no retryAfter; {ok: true} otherwise, an empty list included.
    livePollFailure(error, now?) both pages The outcome of a request that failed: {ok: false}, with notBefore when the answer is a 429 or a 503 that carries a usable Retry-After, in seconds or as an HTTP date.
    computeDirection(current, prev) both pages 'up', 'down' or 'neutral' — neutral when either value is missing or both are equal.

    Callers never block on it: they fire the request, keep what they show until the answer arrives, and on an error keep the last known value. Each poll then returns its outcome to the poller — livePollOutcome(…) after an answer, livePollFailure(error) after a failed request — and the outcome spaces the next poll.

    🔁 Where prices are polled

    Poll Interval Runs while Asks for Feeds
    Assets list (routes/(app)/assets/+page.svelte) at once, then every 60 s the date range ends today or later, and the list is not empty every asset of the list: one request up to 1,000 assets, consecutive batches of at most 1,000 beyond (The shared service) livePriceMap → AssetCard, AssetTable
    Asset detail (routes/(app)/assets/[id]/+page.svelte) at once, then every 30 s the date range ends today or later, the asset is loaded, and it has a provider (below) the asset AssetPriceSummary, then today's point of the price chart

    Both polls run on startActivePolling(), so both pause while the tab is hidden and after two minutes without input, and resume by themselves — see Pause and resume. After a failed poll they wait longer, and while every asset they ask about has its provider paused they wait for the first of those pauses to end — see Failures and provider pauses. The three numbers are the constants of lib/features/live-updates/cadence.ts, set by developer decision 31 (2026-10-15): ASSET_LIST_LIVE_INTERVAL_MS (60 s), ASSET_DETAIL_LIVE_INTERVAL_MS (30 s) and LIVE_UPDATES_IDLE_MS (2 min). The detail page is the faster one because it is the page where a fresh price matters. A fourth constant, LIVE_UPDATES_MAX_BACKOFF_MS (10 min), caps the wait after failures (decision 34, D-Z7-1).

    "The date range ends today or later" is the isHeadToday flag of both pages: dateEnd compared with today on the user's calendar, todayIso() (lib/utils/dateOnly.ts), the calendar dateEnd is resolved in (resolveDateSentinel('max') returns todayIso()). Until Z-3 the pages compared it with the UTC date, which is a day off for part of every day: in the evening west of Greenwich it is already tomorrow, so a range ending today read as past (no live price, and the detail summary showed the chart's last close); just after midnight east of Greenwich it is still yesterday, so a range that ended yesterday read as live and polled. When the flag is false, both pages show the last close of the selected range instead, start no poller and ask for nothing.

    📋 Assets list: one poll per set of assets

    The polling $effect does not read the assets array. It depends on isHeadToday and on liveAssetIdsKey — the asset ids, sorted and joined into one string — so it restarts only when the set of assets changes: an asset created or deleted starts a new poller (one poll at once, then every 60 s); the price reloads, which reassign the same assets, do not. The explicit refreshes — Reload All on the Assets tab and the end of a sync in AssetSyncModal — call refreshLivePricesNow(), which is pollNow() on the current poller: one poll at once per user action, and the cadence restarts from it, so a refresh is never followed by a tick a few seconds later. With no poller (the range does not end today, or the list is empty) it does nothing.

    This matters because the endpoint is a write (see Backend): every successful call is a portfolio mutation (isPortfolioAffectingMutation, lib/stores/portfolio/portfolioMutation.ts) that marks the report, risk and lots caches stale — see Domain state. Before 1.2 the effect read assets itself, so every reassignment of the list — several per refresh — fired an extra request, and each of those mutations could cost the correlation tab on the same page the risk answers it was waiting for.

    Each poll rebuilds livePriceMap (Map<assetId, {value, direction}>), the direction comparing the new value with the previous poll's:

    • AssetCard shows the live price (or the asset's last price) with emerald or red text and border while the last tick went up or down; the tint lasts until the next poll.
    • AssetTable uses the live value in the Last price column, coloured the same way. A market quote is formatted with sensitivity: 'public': the same figure for every user, it is not hidden by the privacy toggle.

    fetchLivePrices returns the poll's outcome: livePollOutcome(results) once livePriceMap is rebuilt, and livePollFailure(e) from its catch. That try wraps the whole poll, so an error of the page's own code counts as a failure too.

    🔎 Asset detail: one poll for the summary and the chart

    The detail page runs one poll, in AssetDetailLive (lib/components/assets/detail/assetDetailLive.svelte.ts), which the page creates while it initialises and which reads the page's state through getters: every 30 s, a single POST /assets/prices/current for the asset (#pollLivePriceOnce), whose answer feeds the price summary (#applyLiveSummary) and then the chart's last point (#applyLiveChartHead). It replaced two loops on the same endpoint — the summary every 30 s, the chart head every minute after a 5 s warm-up, so three requests a minute for an asset with a provider — and the chart-head loop kept asking even on a range that ends in the past.

    The instance's effect reads assetInfo, displayCurrency, fxConversionMissing, isHeadToday and, through a $derived boolean, providerAssignment — nothing else from the page. It re-runs when one of the first four changes or when a provider code appears or goes, and each run that finds the range reaching today, an asset and a provider code starts a new poller, so one poll at once. An answer that lands after the effect re-ran — another asset, another currency, the provider code gone — changes nothing on the page: each run hands the poll its own isCurrent() check, read after the price request, after the conversion and before the chart head, and the poll also checks that the asset is still the page's.

    Without a provider code (Z-8) — a manual asset, or any asset until its assignment has loaded — no poller starts, updatesState (the page's data-live-updates) is stopped and nothing is asked: without a provider POST /assets/prices/current only echoes the stored price, and every answer would still count as a portfolio mutation (Still a write). The effect reads the code through hasProvider (!!providerAssignment?.provider_code), a $derived declared in the constructor and lazy, so building the instance reads nothing from the page. Through the boolean, the assignment reloaded with the same code — reloadMetadata() reassigns it with a new object after a sync or an edit — or with another one does not re-run the effect: the poll asks the backend, which reads the assignment of the moment. That reload also reassigns assetInfo, which does re-run the effect.

    #pollLivePriceOnce returns the poll's outcome: livePollFailure(error) when the request fails; otherwise livePollOutcome([toLivePriceResult(item)]) (of an empty list when the answer has no item), worked out before the isCurrent() checks and returned on every path after them. An error of #applyLiveSummary or #applyLiveChartHead is not caught: the poller counts the throw as a failure.

    #applyLiveSummary sets currentPrice, which the page shows in AssetPriceSummary instead of the last chart close. When the display currency differs from the asset's, the price is converted for today through POST /api/v1/fx/currencies/convert — the UTC date on purpose: the lookup fills backward, so either calendar gives the latest stored rate; if that fails, the native price is shown with the asset's currency and a ⚠ tooltip (conversionFailed, passed as livePriceConversionFailed).

    The direction compares the native values of two consecutive polls, so switching the display currency never fakes a tick, and the first poll after a (re)mount is neutral.

    ✨ Price flash

    On an up or down tick the instance sets direction and increments flashToken, which the page passes to AssetPriceSummary as livePriceDirection and livePriceFlashToken. AssetPriceSummary re-keys the price element on the token ({#key}), so the animation restarts even on two ticks in the same direction, and applies .lf-price-flash-up or .lf-price-flash-down (src/app.css): the number jumps to emerald or red and eases back to its resting colour in 1.3 s. LIVE_PRICE_FLASH_DECAY_MS (1300 ms, exported by the module) then resets the direction to neutral. Under prefers-reduced-motion the colour swaps without the animation and the same timer clears it. When the effect re-runs (another asset, display currency or FX gap, the range no longer reaching today, a provider code that comes or goes) or the page goes away, its cleanup stops that timer and puts the direction back to neutral too, so a flash cut short never stays lit. Test hooks: data-testid="asset-detail-live-price" and data-live-price-direction.

    📈 Chart head

    #applyLiveChartHead merges the polled close into today's point of the page's chartData, through the input's setter (mergeChartPointsIncremental), when it changed — no reload, no flicker. The fields the answer does not carry (original_close, backward_fill_info…) stay on the point, and the signals, derived from chartData, recompute. It does not check the provider: no poll runs for an asset without one (above) — the endpoint would only echo the last stored close, with nothing to merge — and an answer still in flight when the code goes is dropped by isCurrent(), so the chart head never sees such an answer. It skips the answer while the chart, or the calendar of returns, is reloading, and when the answer has an error or no as_of_date; a close equal to the one already charted for that date changes nothing. The comparison is made in the asset's own currency, the poll's: the point's native close, original_close ?? close, since in a converted chart close is in the display currency and original_close holds the native one. In a chart converted to another currency (the polled close is in the asset's own currency) or in calendar-return mode, a close that changed reloads the chart silently (loadChartData(true)) instead of merging.

    ⏸️ Pause and resume

    A live poll runs only while someone is using the page. A tab in the background, or one left open with nobody at it, sends nothing: it stops costing requests to the server and to the price providers, and no longer keeps a cloud instance awake. Both pages get this from lib/features/live-updates/:

    File Role
    cadence.ts The three numbers of decision 31 (see above), and the cap of the wait after failures
    activityTracker.ts Whether someone is using the page: the time of the last input, and whether the tab is visible
    activePolling.ts startActivePolling(): the cadence, the wait after failures, the pause and the resume
    LiveUpdatesStatus.svelte The «Updates paused» pill 
    stateDiagram-v2
    state "paused-idle" as pausedIdle
    state "paused-hidden" as pausedHidden
    [*] --> running: start in a visible tab
    [*] --> pausedHidden: start in a hidden tab
    running --> pausedIdle: no input for idleMs
    running --> pausedHidden: tab hidden
    pausedIdle --> pausedHidden: tab hidden
    pausedIdle --> running: input, or pollNow()
    pausedHidden --> running: tab visible again
    running --> stopped: stop()
    pausedIdle --> stopped: stop()
    pausedHidden --> stopped: stop()

    👀 The activity tracker

    getActivityTracker() returns the tracker of the browser tab: created on first use, shared by every poller, and kept across route changes. It adds its listeners once, at creation:

    • on window, in the capture phase and passive, to pointermove, pointerdown, keydown, wheel and touchstart (ACTIVITY_EVENTS). An input only stores a timestamp — pointermove fires many times a second — and signals activity only while a poller is subscribed;
    • on document, to visibilitychange: the tab going to the background signals hidden; coming back counts as input and signals visible.

    Scroll is not an input: the app scrolls the page itself (guides, scrollIntoView), and a user's scroll already shows as wheel or touchstart. touch() marks activity now: a poller calls it when it starts in a visible tab, since a page that starts to poll follows a user's navigation, and on pollNow(). The tracker is built by createActivityTracker({target, document, now}): getActivityTracker() passes window, document and Date.now, the unit tests their own; dispose() removes its listeners.

    ⏱️ startActivePolling

    const poller = startActivePolling({
    run: fetchLivePrices,                    // one poll, which returns its outcome
    intervalMs: ASSET_LIST_LIVE_INTERVAL_MS, // between the starts of two polls
    onstatechange: (state) => (liveUpdatesState = state),
});
poller.pollNow(); // a refresh the user asked for
poller.stop();    // in the effect's cleanup
    Option Default Meaning
    run — One poll. It may return a PollOutcome, {ok?, notBefore?}. A throw or a rejected promise is caught and is a failure, like {ok: false}: the state stays, and the next poll waits longer.
    intervalMs — Between the starts of two polls.
    idleMs LIVE_UPDATES_IDLE_MS (2 min) No input for this long pauses the polls; 0 never pauses for inactivity, but a hidden tab still does.
    initialDelayMs 0 Delay of the first poll, which always starts from a timer.
    maxBackoffMs LIVE_UPDATES_MAX_BACKOFF_MS (10 min) The longest wait after failures in a row; the wait never drops below intervalMs.
    onstatechange — The initial state, then every change, each reported once.
    tracker the tab's tracker Injected by the unit tests.

    It returns {state, pollNow(), stop()}, the state being running, paused-idle, paused-hidden or stopped:

    • Start — in a visible tab: running, touch(), and the first poll after initialDelayMs. In a hidden tab: paused-hidden, and no poll until the tab is visible.
    • Cadence — a poll starts every intervalMs, counted from the start of the previous one; after failures the wait is longer, and the next poll never starts before notBefore (Failures and provider pauses). A poll still in flight when the next is due makes that tick skip: two polls never overlap, and when it lands the next one starts at the following step of the same cadence — landing late buys no extra poll.
    • Pause — at once when the tab goes to the background: the timers are cleared, a poll in flight still lands (its outcome still counts), none starts. And at lastActivity + idleMs: a single timer waits for that threshold, inputs in between only move the timestamp, and the timer re-arms on the newer one when it fires — so the pause comes at the threshold itself, even between two ticks.
    • Resume — on the first input while paused-idle, or on the return to the tab: running, with one poll at once if the next one is already due — the wait has passed since the start of the last poll (or there was none), and so has notBefore — otherwise at the time it is due.
    • pollNow() — marks activity, ends a pause and polls at once, and the cadence restarts from that poll. This poll was asked for, so it skips the visibility and idle checks, the wait after failures and notBefore; its outcome counts like any other, and the polls after it apply them all again. With a poll still in flight it starts none, and the next poll follows that one's start and outcome.
    • stop() — no poll and no listener afterwards, and a second call is harmless; it does not abort a poll in flight.

    A pause keeps what the page shows: the first poll after a resume compares its value with the last one before the pause, so it can tint a card or flash the price.

    🐢 Failures and provider pauses

    run tells the poller how the poll went by what it returns, a PollOutcome (activePolling.ts):

    export interface PollOutcome {
    ok?: boolean;       // false: the poll failed, and the next one waits longer
    notBefore?: number; // a Date.now() time before which the next poll does not start
}
    • A failure is a run that throws, rejects or returns {ok: false}. Anything else is a success, undefined included.
    • The wait, from the start of one poll to the start of the next, is intervalMs until a poll fails. After k failures in a row it is intervalMs × 2^k, capped at maxBackoffMs and never shorter than intervalMs. The first success brings back intervalMs.
    • notBefore is a floor: the next poll starts at the later of the end of the wait and notBefore. Only the latest outcome counts: an outcome without notBefore clears it.
    • A resume waits for both; pollNow() ignores both, and its outcome counts.
    • A slower cadence is not a state: the poller stays running, the «Updates paused» pill does not show, and the page keeps what it shows. The idle and hidden pauses apply as usual.

    With the default cap, the waits after failures in a row:

    Failures in a row Assets list (60 s) Asset detail (30 s)
    1 2 min 1 min
    2 4 min 2 min
    3 8 min 4 min
    4 10 min 8 min
    5 or more 10 min 10 min

    Both pages build their outcome with livePriceService (The shared service):

    • An answer goes through livePollOutcome(results). An asset whose provider is paused after «too many requests» comes back RATE_LIMITED, with the last stored price, if any, and retry_after (Backend). When every asset asked about is RATE_LIMITED and each one knows its retryAfter, the outcome is a success with notBefore at the end of the shortest pause: the wait is known, so it does not double. When one of them has no retryAfter, the pause has no known end: the outcome is a failure, and the wait doubles. As long as one result is not RATE_LIMITED, the outcome is a plain success and the cadence goes on: such a poll costs little, since the backend does not call the paused providers. On the list, one asset without a provider is enough.
    • A failed request goes through livePollFailure(error): a failure, with notBefore when the answer is a 429 or a 503 that carries a usable Retry-After, in seconds or as an HTTP date. The backend sends no Retry-After on this endpoint today; a proxy in front of the server can.

    Nothing new shows during a provider's pause: the page keeps showing the last stored price that the answer carries, with no new text (decision 34, D-Z7-2).

    🧵 Why every poll starts from a timer

    A page creates its poller inside an $effect. A poll started synchronously by startActivePolling() would run inside that effect, and the effect would subscribe to everything the poll's synchronous head reads. On the Assets list, fetchLivePrices reads assets: the effect would re-run on every reassignment of the list, and every re-run would send one more write (see Assets list). So the helper never calls run inside the call that starts or nudges it: the first poll, every tick, the poll of a resume and the one of pollNow() all start from setTimeout — 0 ms for "at once". The list page used to guard its first call with untrack(); the helper makes the rule hold for every page.

    🏷️ The published state and the pill

    The list keeps the poller's state in liveUpdatesState, the detail page in live.updatesState (AssetDetailLive, handed to AssetDetailHeader as its liveUpdatesState prop) — through onstatechange, and stopped while there is no poller — and each publishes it twice:

    • as data-live-updates on its root, data-testid="assets-page" or data-testid="asset-detail-page" — what the E2E reads;
    • through <LiveUpdatesStatus state={liveUpdatesState} />: beside the title on the list, at the end of the header's chips row on the detail page.

    LiveUpdatesStatus draws only in paused-idle: a pill with a pause icon and Updates paused (liveUpdates.paused), whose title reads Live prices refresh again as soon as you use the page. (liveUpdates.pausedHint), with role="status", data-testid="live-updates-status" and data-state. It is a signal, not a command: it holds no button, because the next input resumes the polls and the pill goes away by itself. It draws nothing in the other states — running, stopped, or paused-hidden, where nobody would see it. Its colours are colour roles, STATUS_TONES.liveUpdates.paused in lib/theme/toneClasses.ts, which follow the theme by themselves; its strings belong to the liveUpdates subsystem of the translation sources.

    ✍️ Still a write

    Pausing does not turn the poll into a read. Every poll that runs is still POST /assets/prices/current, which persists today's candle (Backend): now that it runs only while someone uses the page, it is that user's active update of today's price, and isPortfolioAffectingMutation() keeps counting it as a portfolio mutation, so the portfolio views are marked stale and refreshed in the background (Domain state). On the list a poll over more than 1,000 assets is one request per batch (The shared service), and each batch that succeeds persists today's candles of its assets and counts as a mutation: the views hear it once per batch, which since decision E1 only marks them stale for a background refresh, nothing thrown away. What changed is how often it happens: on the detail page, two requests a minute instead of three for an asset with a provider, and none for an asset without one, which had two a minute until Z-8, each an echo of the stored price counted as a mutation; on the list, one poll instead of two, each a request per batch of at most 1,000 assets; none on a range in the past, and none from a tab nobody uses; fewer still after failed polls, or while every provider asked about is paused (Failures and provider pauses). Today's candle does not depend on an open tab: the scheduler's current-price refresh calls the same service on its own schedule (Scheduler).

    🔄 Updating prices…

    When the server catches up on prices — at its start, at the first request after a minute of silence, at a scheduled wake-up — the web app shows the instance notice Updating prices… while one of the catch-up's jobs runs and, once the catch-up has brought something up to date, marks the portfolio views stale and reloads, by itself and in silence, the views already on screen: the Dashboard, a broker's page, the Assets and FX pages, the risk and lots panels. lib/features/price-refresh/priceRefresh.ts does it, on the startActivePolling() of the live prices. The server's side — what a catch-up is, the header, the route — is in Catch-up Progress.

    📥 The header

    The response interceptor of lib/api/zodios-client.ts hands the headers of every successful answer to priceRefresh.observe(response.headers), right after notifyPortfolioMutation(); a failed answer goes to the error interceptor and is not read.

    • readPriceRefreshHeader(headers) reads x-librefolio-price-refresh (PRICE_REFRESH_HEADER, in lower case, as axios exposes it) through the get() of axios's AxiosHeaders, or as a key of a plain object. It trims and lower-cases the value, and returns starting, running or null (no header, or any other value).
    • observe() does nothing while the tracker ignores the headers after a 4xx (After a 4xx), and nothing on null. On running it shows the notice at once. On either value, when no tracking is under way, it starts one: startActivePolling({run: check, intervalMs: PRICE_REFRESH_POLL_MS}), with its counters at 0.

    Every successful answer means the public ones too: the pages without a session hear the header like the others. They are the sign-in page, whose LoginCard loads the instance configuration, and the invitation, password-reset, email-verification and setup pages, which send the token of their link through the API client; opening one on a quiet instance starts a catch-up by itself. Such a page starts a tracking like any other, and its first question settles it (After a 4xx).

    The header reaches the web app on the answers it gets anyway, at load or later, from the moment the server announces a catch-up: a status asked only at load would miss one that starts later, such as a scheduled wake-up while the app is open. And without the header the web app asks nothing, so an instance with nothing to catch up can still sleep.

    ⏱️ The questions

    check() asks GET /api/v1/system/price-refresh every 3 s (PRICE_REFRESH_POLL_MS) with fetch(PRICE_REFRESH_STATUS_PATH, {credentials: 'same-origin', headers: {Accept: 'application/json'}}), not through the API client, because of the pages without a session. There the question gets a 401, and through the client that 401 would reach its error interceptor, whose way to the sign-in page would leave the invitation, password-reset, email-verification and setup pages without the token of their link, already out of the address. The interceptor now spares those pages (A 401 on a Link Page), but the poll does not depend on that list: a fetch answer goes through none of the client's interceptors, nor through its Zod validation; one that is not ok throws PriceRefreshStatusError, which carries its status.

    The poller is startActivePolling(), for the same reasons as the live prices:

    • the first question goes at once, from a timer; in a background tab, none goes until the tab is visible;
    • the questions pause in a background tab and after two minutes without input: each one is a user's request for the server's idle suspension, and a tab nobody uses must not keep the instance awake. Meanwhile the notice stays as it was, and the question of the resume settles it;
    • after a failed question the next one waits twice as long: 6, 12, 24, then 48 s (Failures and provider pauses).
    Answer What the tracker does
    running Shows the notice, if it is not shown yet, and sets the starting count back to 0
    starting Counts it. The tenth starting answer since the tracking began, or since the last running (PRICE_REFRESH_MAX_STARTING_POLLS), ends the tracking: the run never came
    idle, or any state but those two Ends the tracking, the notice hidden; then asks the portfolio views to refresh, when a job of this catch-up was seen running and last_refreshed is true
    A 4xx Ends the tracking at once, the notice hidden, without a refresh, and the headers are ignored from then on: see After a 4xx. It is not a failure
    A 5xx, a network error, or a body that is not JSON A failure: the poller waits longer. The fifth failure in a row (PRICE_REFRESH_MAX_FAILURES) ends the tracking, the notice hidden

    Any answer sets the failure count back to 0, and an answer that lands after its tracking has ended changes nothing. Once a tracking has ended, the next answer that carries the header starts a new one.

    The portfolio refresh. "Seen running" means a running header or answer during this tracking: a catch-up with nothing due never shows one, and the last_refreshed read at idle would then be an older catch-up's. The refresh is notifyPricesCaughtUp() (lib/stores/portfolio/portfolioMutation.ts), which dispatches {kind: 'prices'} on the portfolio bus. It is a signal of its own, so that a page on screen can tell the end of a catch-up from a write ({kind: 'mutation', …}) and from its own Refresh button (requestPortfolioRefresh(), {kind: 'refresh'}), which already reloads the page, with force. The report, risk and lots caches mark their answers stale on any signal and keep them, showing what they have while the view asks again (Domain state). The views on screen ask again at once, as The reload says.

    Two helpers do the second half:

    • Dashboard and broker page keep their own listener, reloadAfterPriceCatchUp(), described below.
    • Every other view calls onPricesCaughtUp(reload) (lib/features/price-refresh/onPricesCaughtUp.ts), once per call, in its lifecycle, and keeps the function it returns to stop it. It ignores mutation and refresh; on {kind: 'prices'} it queues reload with queueMicrotask(), so the reload runs after the dispatch, when every cache has already marked itself stale. A reload that throws or rejects is logged and never rethrown: the view's own request code reports its failures, and one view must not stop another's reload.

    The views that call it, and what each reloads:

    View Reloads, without force
    Risk panels (riskPanelController.svelte.ts) loadBase(false, true), only when a base wave is on screen. The on-demand analyses the user ran (comparison, stress, replay, simulation) are left as they are
    Lots panel (LotsAnalysisPanel.svelte) The main analysis and the selection histories, only while the panel is open, with an asset and ready

    FX pair page (fx/[pair]/+page.svelte) loadChartData(…, silent), the comparisons and the signal pairs

    In silence means a silent argument down the page's own request code: the loading, signalsLoading and calendar loading flags stay off, and the risk controller keeps refreshing false, so nothing spins and nothing is dimmed. Rule D3: a price or FX store that a catch-up marked stale and that still holds points for the range (TimeSeriesStore.isStale) shows them at once, and the page asks the server in background with no loading state; a store with no points for the range loads as on a first visit. isStale is read-only and stays set until invalidateAll(): a fetch covering the range clears the gaps, not the flag.

    Two pages also reload while on screen: the Dashboard (routes/(app)/dashboard/+page.svelte) and the broker detail page (routes/(app)/brokers/[id]/+page.svelte). Each registers a bus listener in onMount, dashboard:prices or broker-page:<id>:prices, and removes it on destroy. On {kind: 'prices'}, and on no other kind, the listener queues reloadAfterPriceCatchUp() with queueMicrotask(): the reload runs once the dispatch is over, when every cache has marked its answers stale, whatever the order of the listeners. The reload calls the page's report loader without force, in background: loadAll() on the Dashboard, loadOverview() on the broker page. The mark has made the report on screen stale, so the loader asks that question again; the figures stay until the new ones land.

    It touches neither refreshVersion nor requestPortfolioRefresh(), the signals of the user's Refresh (they spin the icon and say the page is busy): the caches are already marked, and the risk and lots panels on screen reload on their own onPricesCaughtUp. Nor does it hold the Refresh button. Since Y11 (decision 48) the button of each page, sync-button on the Dashboard and broker-refresh on the broker page, follows pageBusy.busy (lib/stores/app/pageBusy.svelte.ts): it spins, disabled, while one of the page's big requests is pending — a load the page starts on a trigger (the first load, a Refresh, a change of period or currency), wrapped there in pageBusy.track(), or a panel's own load, which pageBusy.join() counts only while one of those is pending. The reload is wrapped in neither, so no Refresh button waits or spins while it runs.

    On the Dashboard the call is loadAll(false, false, {background: true}), and the option keeps the page from saying it is busy (Z-18): a screen reader would announce «busy» for a price refresh nobody asked for. The root (data-testid="dashboard-page") binds aria-busy and data-busy to reportLoading || contributionLoading || contributionRefreshing || syncLoading. With background, loadAll() does not turn reportLoading on, and loadContribution({background}) asks a stale cached contribution again under contributionInBackground instead of contributionRefreshing: a non-reactive flag that keeps a second request from leaving, as contributionRefreshing does, but that the root does not read. The reload thus turns neither attribute on, while a load the user asks for still does; and it does nothing once the page is destroyed (pageAlive). On the broker page loadOverview() has no such option: the reportLoading it turns on only shows the skeletons drawn while no figures are on screen yet, and the page's root publishes no aria-busy. The broker summary (loadBroker()) and the transactions, which that page's Refresh asks again too, are left as they are.

    The pages in the table above reload the same way. The broker list (routes/(app)/brokers/+page.svelte) does not listen: it reads the caches the signal marked stale, so it asks again the next time it loads; the live prices of the Assets list and of an asset's page keep their own polling (Where prices are polled).

    The price and rate series that the asset pages and the FX pages keep in their session caches (lib/stores/assetPriceStoreRegistry.ts, lib/stores/fxStoreRegistry.ts) go stale too, on prices and on no other kind: each registry listens on the bus from its import and marks every store stale, keeping its points (Registries & Caches). The next visit of a price or FX page, or its next change of range, asks the server again, once, and puts on screen the points the store still holds (isStale), asking in background, instead of the loading state of a first visit; the market rate a transaction modal compares an exchange with (lookupFxRate) is asked again for its day. A page already open during the catch-up reloads by itself, as The reload says (Z-14b).

    🚫 After a 4xx

    A 4xx is a status from 400 to 499: the status of a PriceRefreshStatusError, or the axios-like response.status of an error that an injected fetchStatus throws. It means this page cannot follow the catch-up: it has no session (401), or the instance is blocked (423). The tracker ends the tracking at once, hides the notice and asks no refresh; the answer does not count as a failure. Then it stops listening (its suspended flag): observe() ignores every header until reset(), at the next change of the signed-in account — for a page without a session, the sign-in — or until the next page load. stop() alone does not lift it. A sign-in page left open thus asks once at most, then nothing more.

    📢 The notice and the session

    The notice is {id: 'liveUpdates.priceRefresh', severity: 'info', messageKey: 'liveUpdates.priceRefresh.running'} (PRICE_REFRESH_NOTICE_ID, PRICE_REFRESH_MESSAGE_KEY), shown with instanceNotices.show() and removed with hide(): see Instance notices. It is not dismissible: it goes away by itself, when the tracking ends. InstanceNotices.svelte draws it above every page of the app shell, with role="status", data-testid="instance-notice", data-notice-id="liveUpdates.priceRefresh" and data-severity="info": no markup of its own, and the colours are the notice component's. Its text, Updating prices…, belongs to the liveUpdates subsystem of the translation sources.

    stop() ends the tracking: no more questions, the notice hidden if shown, the counters at 0. reset() does the same, and also lets the headers through again after a 4xx: the app calls it through registerClientSessionReset('priceRefresh', …) when the signed-in account changes, a sign-in or a sign-out, so no tracking and no notice outlive the account that saw them.

    createPriceRefresh(deps) builds a tracker with its collaborators — fetchStatus, notices, refreshPortfolio and startPolling — so a test can pass its own. The module exports the app's tracker, priceRefresh, built with the defaults: the fetch above, instanceNotices, notifyPricesCaughtUp() and startActivePolling(). The defaults reach those modules when they are called, not when the module loads: the API client imports this module, and a test that mocks one of them only in part, such as the client's own tests, must still load it.

    The default notices goes further: it loads the registry on first use. instanceNotices.svelte.ts holds runes, so priceRefresh.ts imports only its InstanceNotice type (import type); the first show() or hide() loads the module with import(), through one promise that every later call shares, which keeps a hide() from overtaking its show(). The API client imports priceRefresh, and the client must stay free of runes: the AI Export probe loads it without Svelte's compiler, and a gate checks it (the probe's frontend bridge). The notice thus reaches instanceNotices a few microtasks after the tracker shows or hides it, which nothing visible depends on; a tracker built with deps.notices, as the tests build theirs, calls its sink at once.

    The live-pause E2E drives time with page.clock, since minutes of cadence can be neither waited for nor guessed, and answers POST /assets/prices/current in the browser with an empty, schema-valid result — or, in (g) and (h), with a failure or a provider pause, and in (j) with a provider quote — that it counts: nothing reaches a provider and nothing is written. (i)–(l) set the browser's time zone (timezoneId) and install the clock at a chosen instant of that zone's evening or night, then read the page's calendar — its time zone, its local date, its UTC date — before counting anything, since the two dates agree for most of the day. A hidden tab has no Playwright API, so the spec redefines document.visibilityState and dispatches visibilitychange, which is exactly what the tracker listens to.

    The price-refresh E2E, desktop only, never waits on a real catch-up of the shared backend. One route on **/api/v1/**, installed after the sign-in, answers the status route in the browser with what the case scripts, and passes every other request to the backend (route.fetch()), giving the page the real answer with the case's header, or with none. Time runs on real timers. An init script records in the page every report request and every status answer read, the latter one task later, so a reload that answer caused is already recorded and an absence is read exactly; for (g) and (h) it also records each price or rate query a chart sends, with its body and what its answer held. The one write on their path, the asset page's live poll, is answered in the browser with an empty result, as in the live-pause E2E. Nothing is written.

    ⚙️ Backend

    POST /api/v1/assets/prices/current takes a list of asset ids and answers FACurrentPriceResponse (results, success_count). get_current_prices_bulk (backend/app/services/assets/price_query.py) resolves every asset in parallel:

    sequenceDiagram
    participant Page as Assets list / asset detail
    participant API as POST /assets/prices/current
    participant Prov as Assigned provider
    participant DB as PriceHistory

    Page->>API: [asset_ids]
    opt provider assigned, no quote in the 2-min cache
        API->>Prov: get_current_value(), 10 s timeout
        Prov-->>API: value, currency, as_of_date
    end
    alt quote, fresh or cached, kept by storable_current_value()
        Note over API: served as the price columns keep it, a fresh quote cached 2 min
    else no provider, the provider failed or is paused, or its quote is refused
        API->>DB: latest stored close that reads a number
        DB-->>API: value, source db:last_known
    end
    API->>DB: upsert today's row, fresh provider quotes dated today only
    API-->>Page: results with asset_id, value, currency, as_of_date, source, error, error_code, retry_after
    • A provider answer has source: "provider:<code>" and is served as the price columns keep it (storable_current_value(), backend/app/services/assets/price_store.py; X-R40, W-B62): in its own form when the history's truncation leaves it unchanged (101.5 stays 101.5), truncated otherwise (65432.1234567890999 → 65432.123456789). Only such a quote is cached, for two minutes (_asset_current_cache, backend/app/services/assets/core.py, shared with the price sync), and a cached one is served the same way.
    • A refused quote, one no price column can keep (not finite, more than 12 digits before the decimal point, or non-zero but 0 once truncated to 12 decimal places, such as 1E-13) or, since N92, one not above 0, is neither served, cached nor written: the asset falls back to the database exactly as after a provider failure, with no error_code, and the next poll asks the provider again. The backend logs it once per asset, provider and value: Current Quotes and Today's OHLC.
    • The database fallback is the latest stored close that reads a number, with source: "db:last_known": a close the file holds as ±inf reads as no value and is passed over. An asset with no price at all comes back with value: null and an error.
    • A paused provider is not called: while the asset's provider is paused after «too many requests», or when it refuses this call, the answer is the last stored price (source: "db:last_known", still HTTP 200) with error_code: "RATE_LIMITED" and retry_after, the seconds until the provider may be called again; with no stored price, an error and the same two fields. The pauses are the backend's: Provider Pauses.
    • Side effect: a provider quote dated today creates or extends today's PriceHistory row, with the value served. A database fallback is never written back. This write is why the frontend treats the call as a portfolio mutation.
