    🧪 Designer Lab

    The Designer Lab is a hidden page, /designer-lab, that exists only in debug builds. A designer opens it in one browser tab and changes the app's colours; the app, open in other tabs of the same address, repaints at once — charts included. The designer can also point at an element in an app tab: the Lab shows what sets each of its colours in the code, and can change one of them for that component alone. At the end of a round the Lab exports the changes, with the file and line of every occurrence, so that an agent can apply them to the code.

    • Designers edit colours while looking at the real app: no code, no install.
    • Developers start the server for them and receive the export.
    • Agents verify the export and apply it with the skill designer-lab-apply.

    Developer tooling, not a feature

    The Lab never reaches a release build, calls no backend API and stores nothing on the server. It has no entry in the user changelog, and its texts stay outside the app's translation catalogue.

    🚦 Availability: Debug Builds Only

    🔀 The Build Switch

    __LF_DESIGNER_LAB__ is a constant replaced at build time (define in frontend/vite.config.ts, declared in src/app.d.ts). Its value comes from designerLabEnabled() in frontend/scripts/designer-lab/vite-plugin.mjs:

    Build __LF_DESIGNER_LAB__
    VITE_DEBUG=true: npm run build:debug, ./dev.py front build --debug true
    vite build --mode development true
    vite dev (npm run dev) true
    npm run build, ./dev.py front build (release) false
    LF_DESIGNER_LAB=1 or LF_DESIGNER_LAB=0 in the environment forced on or off, whatever the build

    LF_DESIGNER_LAB=0 gives a debug build without the Lab, to compare two gallery captures with and without it.

    The value is a literal, so a release build turns every if (__LF_DESIGNER_LAB__) into if (false): Rollup drops the branch and the dynamic import() inside it, and no Lab chunk is emitted. Three places import the Lab inside such a branch:

    File What the branch does
    src/routes/+layout.svelte (onMount) Imports and starts the Lab client, on every page
    src/routes/designer-lab/+page.ts load() answers error(404) when the switch is off
    src/routes/designer-lab/+page.svelte Imports DesignerLab.svelte in onMount 
    // src/routes/+layout.svelte — onMount
if (__LF_DESIGNER_LAB__) import('$lib/dev/designer-lab/client').then((lab) => lab.start()).catch(() => {});

    A fourth branch, in src/lib/theme/chartCategories.ts (workstream DV), imports nothing: it asks the published hook for an edited category colour, and a release build drops it too — see Chart Categories.

    🧪 Test Server, E2E and Gallery

    ./dev.py server --test always builds and serves the debug bundle: --test forces debug mode, and frontend/build/.build-debug records the mode of the last build. The E2E runs and the gallery use the test server, so they all load the Lab client, and they must stay identical as long as nobody uses the Lab. They do, because in a browser context where the Lab was never opened — every gallery context, and every E2E context but those of the Lab's own specs — the client stays idle:

    • the client publishes its debug hook and adds one storage listener: it loads no engine and no picker, and touches no stylesheet, variable or chart. The hook's categoryColor, which every chart asks for its categories, answers nothing, so the charts keep their tables' colours;
    • the Alt+Shift+D shortcut adds one keydown listener, and only in a browser where the Lab has been opened (lf-designer-lab/seen, written by the Lab page);
    • the engines and the element picker are dynamic imports, separate chunks loaded the first time a state with an effect, or a pick request, appears.

    Measured on 14/10/2026 in a debug build: the client chunk weighs 6.2 KB and reaches the picker (73.6 KB, test-id index included) and the engines only through dynamic imports.

    🛡️ Release Builds

    • /designer-lab keeps only a stub. The backend's SPA fallback answers the URL with 200.html (HTTP 200), then +page.ts throws the 404 and the client renders +error.svelte.
    • The Vite plugin guards the switch in a build without the Lab:
      • generateBundle fails the build when an emitted file contains the marker lf-designer-lab, and names the files. The Lab's code carries it in its storage keys, in the ids of the styles it injects, in its cascade layer and in its dev-server event;
      • load fails the build if anything imports virtual:lf-color-catalog or virtual:lf-testid-index.
    • Checked on 14/10/2026 with the element picker in place: npm run build emitted no file with the marker and no trace of the picker or of the test-id index, and the /designer-lab stub node kept its 488 bytes.

    Import the Lab only inside a branch

    Every import of $lib/dev/designer-lab must be a dynamic import() inside an if (__LF_DESIGNER_LAB__) branch. A static import would carry Lab code into the release bundle; the marker guard stops ./dev.py front build when that code holds the marker, as the client's store, the engines and the page do.

    🔓 No Login

    The route sits outside the (app) group: no login and no app shell. The Lab calls no API — it reads the catalogue bundled with the build and the state saved in the browser. The app in the other tabs asks for its login as usual.

    🎨 Opening It for a Designer

    scripts/visual_review/designer_live.sh starts a test server for a designer's review on its own lane: port 6160, data in /tmp/librefolio-color-review, copied from the latest gallery run (--from picks the source lane, --refresh copies it again). The server listens on 0.0.0.0, so a designer on the same network can reach it.

    # In a linked worktree, reuse the main venv: the script refuses to start without it
export PIPENV_CUSTOM_VENV_NAME=<main venv name>
scripts/visual_review/designer_live.sh
    • The Lab: http://<this-machine>:6160/designer-lab.
    • The app, in other tabs: http://<this-machine>:6160, logged in with the E2E admin user the script prints.

    --test already serves the debug build: the Lab is there without the script's --debug option.

    ./dev.py server lists http://localhost:<port>/designer-lab in its «Available endpoints» whenever the build it serves holds the Lab's marker: a --test or --debug build, not a release or LF_DESIGNER_LAB=0 build. ./dev.py front dev (port 5173) prints it too, unless LF_DESIGNER_LAB=0.

    One address for every tab

    The state and the picker's messages live in localStorage and travel through the storage event, both scoped to one origin. http://localhost:6160 and http://192.168.1.20:6160 are two origins that share nothing: open the Lab and the app with the same host name.

    🏗️ Architecture

    The Lab has two halves. The catalogue, built from the sources at build time, gives completeness and provenance: every colour of every file, with file and line, even in components the page has not loaded. The runtime engines give the immediate preview, acting on what the browser has really loaded. The export joins the two: what changes, and where. The element picker starts from the other end: from an element on screen, it proves which declaration sets each of its colours, and the Lab finds that declaration in the catalogue.

    🔄 The Client

    client.ts, with store.ts and pick.ts, is all of the Lab that an app page loads. start() is idempotent: it publishes window.__lfDesignerLab, adds one storage listener, then reads the three keys once, as if each had just changed. The listener follows them (null, which localStorage.clear() sends, counts for the first two):

    Key What the client does
    lf-designer-lab/v1, the state While no engine is loaded, stop unless the state has an effect — not suspended, with at least one change or a colour-vision mode; otherwise import engine/ (a separate chunk) once, and call applyState(state)
    lf-designer-lab/pick, the picker's messages While no picker is loaded, stop unless a start is pending; otherwise import picker/overlay.ts (another chunk) once, and let it follow the message. The Lab's own page never picks
    lf-designer-lab/seen Install the Alt+Shift+D shortcut — see The Two-Tab Flow

    The Lab page writes the state itself, and a tab gets no storage event for its own writes, so the page calls applyNow(). Nothing else runs while idle: no BroadcastChannel, no observer, and no keyboard listener in a browser where the Lab was never opened. The engine adds its observers — theme switches on <html>, late stylesheets in <head> — only while a state is active; applyState(null), or a suspended state, undoes everything and leaves the module loaded but idle.

    💾 The Shared State

    store.ts keeps one JSON document in localStorage['lf-designer-lab/v1'], schema lf-designer-lab-state/1. A state with another schema is ignored.

    Field Content
    changes The changes, in the order they were first made
    suspended Show the original colours without losing the changes
    cvd Colour-vision simulation: none, protanopia, deuteranopia, tritanopia, achromatopsia
    notes, author The general note and its author, both exported
    variants, activeVariant Named snapshots of changes, for A/B comparison
    updatedAt Time of the last write

    A change has an id — <layer>:<target>@<scope>, plus #<literal id> when it is restricted to one stylesheet occurrence, and element:<property>[:<colour key>]@<scope>~<selector> for a specialisation — a layer, a target (a variable name, a colour key, a chart category such as type:ETF, or a specialisation's selector), a scope (light, dark or both), from, to (any CSS colour, var(--x) included), alphaVariants (default true), occurrence and match for a single occurrence, property and colorKey for a specialisation, an anchor (the picked element the change was decided on: set on every element change the Lab makes, context on the other layers), a note and shots. isSafeCssValue() refuses a to longer than 200 characters or holding a semicolon, a brace, an angle bracket, a quote, a backtick, a backslash or a comment opener, so a typo cannot break out of a style rule. isSafeSelector() guards a specialisation's selector the same way: at most 600 characters on one line, without a brace, a semicolon, a < or a comment opener.

    The picker's messages travel under two other keys, outside this document: see The Two-Tab Flow.

    🎛️ L1 — CSS Variables

    engine/vars.ts writes one <style id="lf-designer-lab-vars"> in <head>, with one rule per css-var change. The selector carries the scope (VAR_SELECTOR) and names, besides <html>, the .light or .dark subtrees of the scope's themes: the elements on which the token blocks of tokens.css define the colour roles (Colour Roles):

    /* example values — scope both, light, dark */
html, .light, .dark { --color-emerald-600: oklch(62% 0.13 160) !important; }
html:not(.dark), .light { --theme-text-muted: #5b6370 !important; }
html.dark, .dark { --theme-text-muted: #a3adbd !important; }

    An !important declaration beats every normal one, inside @layer theme or not, so everything that reads the variable follows at once:

    • Tailwind classes, which read the palette at runtime (.text-red-500{color:var(--color-red-500)});
    • their opacity modifiers (color-mix(in oklab, var(--color-red-500) 20%, transparent));
    • the role utilities, which read the role itself (.bg-lf-card{background-color:var(--lf-surface-card)}), and the derived roles built on it;
    • the brand (--color-libre-*) and the --theme-* variables of app.css.

    A .light or .dark subtree — an element forced into one theme, which redefines the roles for itself — gets the overrides of its theme too. The derived roles, which tokens.css defines on :root, .light, .dark, recompute from the overridden values, on <html> and in the subtree alike. applyVars() writes every both rule before the light and dark ones, keeping the changes' order otherwise: when a variable has both kinds of change, the theme's rule wins on <html> anyway (html.dark beats the both rule's .dark), and on an island, where the two rules tie on .dark or .light, it wins by coming later.

    The reach is the variable: changing --color-emerald-600 changes every class that uses it. The editor shows the impact — uses, files, the most used classes, where the sources define the variable. A role's impact counts the utilities that read it through their alias.

    This path serves the variables the whole page inherits, scope: root in the catalogue (:root, html, @theme, html.dark, .light, .dark…), the colour roles included. Variables that a component defines on its own elements (--highlight-*, --cropper-*, --lf-price-flash-*…) are scope: scoped: L2 rewrites their defining rule instead.

    🖌️ L2 — Stylesheet Colours

    engine/stylesheets.ts rewrites colours in the CSSOM: every rule of every readable stylesheet, nested rules (@media, @supports, @layer) included, minus the Lab's own styles (data-lf-lab-own).

    • By parsed colour, never by text. Chrome serialises #64748b as rgb(100, 116, 139) and expands shorthands into longhands: each colour token of a declaration is parsed and compared by its colour key.
    • Reversible. A rewritten declaration keeps its priority and its original text is saved: each new plan, or none, starts from the page as it was.
    • Alpha variants. Translucent writings of the colour share its key and change too, keeping their alpha. A change can opt out (Translucent variants too).
    • Late stylesheets. SvelteKit loads CSS per route. While a plan is active, a MutationObserver on <head> rewrites each <link rel="stylesheet"> when it loads and each <style> as it arrives.
    • Component variables. A css-var change to a variable defined on a non-root rule rewrites that definition.
    • Variables' definitions. A colour written inside a custom property's definition is rewritten like any other, and the variable changes wherever it is read: a role that tokens.css writes as a literal changes with a Stylesheets edit of that value, as with an L1 edit of the role. The charts that read roles when they draw hear of it through the redraw signal, C4 (Chart Categories).
    • One occurrence. A change restricted to one occurrence carries the selector and property that the catalogue recorded. The engine compares them with each rule after normalizeSelector() — .svelte-… scope classes dropped, :global() unwrapped, spaces and case normalised — and accepts a longhand of the recorded property (border → border-top-color). Occurrence changes are tried before value changes of the same colour. While no loaded rule matches them (its component is not on screen), the change shows nothing: by design, the engine does not fall back to every occurrence of the colour. The change is exported all the same.
    • Theme. A light or dark change applies only while that theme is on, whatever the rule's selector; the engine re-plans at every theme switch. The editor warns when a one-theme change reaches rules written for both themes.

    The step 0 spike measured the technique on /transactions: 24 stylesheets and 3,718 rules scanned in 13.5 ms, 33 declarations rewritten in 0.3 ms.

    📈 L3 — Chart Colours

    ECharts options are built in JavaScript: there is no stylesheet to rewrite. engine/charts.ts combines two mechanisms:

    1. A wrapper on the shared prototype. At the first non-empty chart plan the engine imports echarts — the module the app imports, so every instance shares one prototype — takes an instance on screen, or a 1×1 probe on a detached <div>, and wraps setOption on its prototype. From then on every option an instance receives (first render, new data, theme switch) has its colours mapped. With an empty plan the wrapper is a pass-through.
    2. A live re-apply of the instances on screen. The engine finds them through [_echarts_instance_] and getInstanceByDom(), reads each getOption(), builds a sparse patch with only the colour paths that change, and merges it with the original setOption. Component lists at the root get {} placeholders, because ECharts merges them by index; other arrays (data, colorStops, a palette) are sent whole. Zoom and data stay as they are.

    The re-apply exists because forcing a redraw is not enough: at the step 0 spike, 5 of the 17 chart components did not redraw when the class of <html> changed without a theme switch. ScatterChart, CorrelationHeatmap, ExposureBars and ExposureMaps only stored the dark flag, and SemiDonutChart had no observer at all. The spike confirmed it on the correlation heatmap, the scatter and the semi-donut; the re-apply updated 6 instances out of 6, in 1.9–6.8 ms each, with patches of 151–650 bytes. SemiDonutChart now redraws on every class change, while the other four still store the flag only. Some charts also rebuild their option on the Lab's redraw signal, C4 (Chart Categories), which the engine sends when the variables or the categories the charts read change — an L1 edit, a category edit, or a variable's definition the stylesheet pass rewrote — not for chart colours: L3 patches those itself.

    The mapping:

    • is copy-on-write: the app's objects are never mutated;
    • walks strings (rgba() keeps its alpha; tooltip HTML included), gradients (colorStops) and functions: formatter, color and renderItem are wrapped once, and their return value is mapped with the plan in force at call time;
    • is reversible: every string the engine writes is remembered with the original it replaced, so a new plan, or none, starts from the app's own colours;
    • writes canvas colours as sRGB rgba(r, g, b, a) with a four-decimal alpha, clamped to the sRGB gamut: a form no colour of the app uses, so the engine recognises its own output when it reads an option back;
    • keeps one plan per theme, and reads the theme in force when it maps; an instance's plan also takes the chart specialisations whose selector contains it (see below).

    🍩 Chart Categories

    The charts draw each asset type and each sector in a fixed colour, chosen by key: 11 asset-type families and 14 sectors, plus two buckets that both kinds share, Liquidity (the cash) and Unknown. Workstream DV keeps them in frontend/src/lib/theme/chartCategories.ts, under a contract with the Lab:

    • C1, one read point. Every chart reads a category's colour through categoryColor(kind, key, dark): the allocation pie and the allocation history, with their legends and tooltips; the PAC planner's exposure bars, for the actual weights (actualColours() in exposureBarColours.ts: an asset type by its family, its subtypes shaded with familyShade, a sector by its key, the uncategorised remainder as Unknown). The colours borrowed from a category go through it too (see Reach below): the owners of the semi-donut and the countries of the allocation history through sequenceColor, the Growth chart's broker lines and their tooltip rows through growthBrokerColor(). The GR4 subtype shades are mixed from the colour it returns.
    • C2, one literal per line. The tables write one literal per line, each entry under its key, as light: and dark:: an edit is exported by file and line.
    • C3, a hook in debug builds. categoryColor first asks globalThis.__lfDesignerLab?.categoryColor?.(kind, key, dark), inside a typeof __LF_DESIGNER_LAB__ !== 'undefined' && __LF_DESIGNER_LAB__ branch that a release build drops. The app imports nothing of the Lab. The release guard looks for lf-designer-lab, which the name __lfDesignerLab does not hold: the minifier is what keeps the branch out, and DV's chartCategories.test.ts checks it on a minified build.
    • C4, a redraw signal. src/lib/theme/themeMode.ts has onChartColorsChange(cb) and notifyChartColorsChange(): the event lf:chart-colors-change on document. A chart that hears it rebuilds its whole option, so it reads its categories again, and the roles it reads through chartRoles (roleColors.ts, the sRGB bridge).

    By key, not by value. Types and sectors share values (ETF and Technology, BOND and Utilities…), and some category values are written elsewhere too, by a role or another chart: a change of the value in the Charts tab would recolour several categories at once. A category change — the sixth change layer — names one category by its key: type:<KEY>, sector:<Key>, bucket:Liquidity or bucket:Unknown, as the table writes it. Its id is category:<target>@<scope>, and its value any colour the editor accepts: a literal, a var(), a mix with transparent.

    The engine. engine/categories.ts, part of the engine chunk of the app tabs, holds the category changes of the applied state and answers the hook, which client.ts publishes as categoryColor (The Debug Hook). The hook answers nothing until a state with an effect loads the engine, nor while the state is suspended: the table's colour then stands. Otherwise, for a category with a change in the asked theme:

    • a change for that theme wins over one for both, as in L1;
    • the value is resolved at each ask: a var() follows the page's current value of the variable, an L1 edit included, and a value that does not resolve now gives no answer;
    • the answer is a colour the canvas reads, clamped to sRGB: #rrggbb when opaque, the form the GR4 shades mix, and rgba() when translucent;
    • keys go through DV's own lookupKey (chartCategories.ts), as in categoryColor: case, spaces and underscores ignored (Health Care, HEALTH_CARE), so an edit and the table it overrides always agree on what the same key is; the two buckets answer for both kinds.

    stats().categoryOverrides counts the category changes the engine holds.

    The redraw (C4). The engine calls notifyChartColorsChange() when what the charts read at their draw has changed since its last check (signalChartInputs() in engine/index.ts). It compares one signature of it:

    • the css-var and category changes, by id and value;
    • the custom-property declarations the stylesheet pass rewrote, on a root rule or a component's, as selector, property and value (variableRewrites() in engine/stylesheets.ts). The roles of tokens.css, the derived ones aside, are written as literals, so a Stylesheets edit of such a value changes the role.

    The check runs at the end of applyState(), once every engine is applied — a change added, edited or removed, the state suspended, resumed or reset — and again after the theme observer has re-planned the stylesheets. A literal scoped to one theme rewrites a role in that theme only: after the switch the check signals once, whatever order the theme observers ran in, and a chart that redrew before the re-plan reads the role again. Nothing is sent while the signature stays the same: the same changes applied again, and the changes the charts do not read at their draw — stylesheet literals that define no variable, chart colours and chart specialisations (L3 patches the charts already drawn), the colour-vision simulation. The signal brings an edit of a role, from L1 or from the stylesheets, to the charts that read roles through chartRoles — today the allocation pie, the allocation history, the semi-donut, the correlation heatmap and the PAC planner's exposure bars — at once, where it used to wait for their next draw. A stylesheet that arrives later sends no signal of its own (Known Limits).

    Reach. A category's colour is the base of its family's GR4 subtype shades, and the categories without a key of their own borrow it by rank (GR5, sequenceColor): the owners of the semi-donut take the first eight asset types, the countries of the allocation history the sectors. The Growth chart's broker lines borrow the same eight types, cycled without a shade: broker line i takes the colour of the asset type CATEGORY_SEQUENCE[i mod 8] (growthBrokerColor() in src/lib/theme/chartPalettes.ts, read each time the series are built). Every chart that reads a category redraws on C4 — the allocation pie, the allocation history, the semi-donut, the Growth chart and the PAC planner's exposure bars — so a category change reaches all of them at once, the subtype shades and the borrowed colours included: a type edit also recolours the broker lines that borrow it.

    📌 Specialisations — element Rules

    A specialisation changes one colour property of a picked element in every instance of its component, without touching the shared source — the variable, the class or the rule the rest of the app keeps using. engine/anchors.ts writes one rule per specialisation into <style id="lf-designer-lab-elements">, for every theme at once (the prefix keeps them apart, as in L1):

    /* example value — the header cells of the transactions table, light theme */
@layer lf-designer-lab {
html:not(.dark) :is([data-testid="tx-table"] > div > div > table > thead > tr > th) { color: #475569 !important; }
}

    The cascade layer is the point. A <style>@layer lf-designer-lab;</style>, prepended to <head> (id="lf-designer-lab-layer-order"), declares it before any other layer, and among !important declarations the cascade reverses: the first layer wins over the later layers — Tailwind's ! utilities such as !bg-white, in utilities — and over the unlayered declarations — the P1 dark overrides of app.css. So the preview shows the new colour whatever the app writes there; only an inline !important style stays on top. Both styles leave <head> when no specialisation is left.

    A rule is written only when the browser parses the selector, isSafeSelector() and isSafeCssValue() accept the selector and the value, and the property is one of ELEMENT_PROPERTIES (cssProps.ts): color, background-color, border-color (the four sides) or one side's border-*-color, outline-color, text-decoration-color, fill, stroke. The picker reports box-shadow and gradients too, but they cannot be specialised.

    A chart specialisation (property: 'chart', with the colorKey it replaces) writes no CSS. L3 keeps it in a list per theme, and planFor(instance) adds it to the plan of an ECharts instance only when the instance's DOM sits inside an element the selector matches (dom.closest(selector)). Values that functions return — formatter (tooltips), color, renderItem — are computed later, without their instance, and keep the global plan.

    The L2 engine and the picker skip these styles, like every style the Lab injects (data-lf-lab-own), and stats().elementRules counts the rules written.

    👓 Colour-Vision Simulation

    engine/cvd.ts applies an SVG feColorMatrix filter to <html>: protanopia, deuteranopia and tritanopia with the matrices of Machado, Oliveira & Fernandes (2009) at severity 1, in linear RGB, and achromatopsia with the Rec. 709 luminance weights. The root element is the one place where filter does not turn the element into the containing block of its fixed descendants, so modals and sticky headers keep their place. The mode is part of the state: every tab follows, the Lab's own included.

    Theme hint. A list that mixes themes (.a, html.dark .b) applies in both and fixes nothing; both otherwise. In scripts, dark or light from an object key (dark: '#…') or from the side of a ternary whose condition names the dark theme, on one line (isDark ? … : …) or split as Prettier writes it (isDark ending a line, ? '#…' and : '#…' on the next ones); a negated condition (!isDark, !$isDark) swaps the sides. In markup, dark when the class holding the colour carries a dark: variant (dark:bg-[#1e293b]), never from a neighbouring class. null otherwise.

    🎭 Colour Roles

    Workstream T moves the interface colours to colour roles, in frontend/src/lib/theme/tokens.css:

    • a role is a variable --lf-<group>-<name>, such as --lf-surface-card. The token blocks define the roles on :root, html.light, .light (light) and html.dark, .dark (dark), and the derived ones — color-mix(), references to other roles — on :root, .light, .dark;
    • an @theme inline block turns each role into Tailwind utilities: --color-lf-card: var(--lf-surface-card) gives bg-lf-card, border-lf-card, ring-lf-card…

    With inline, Tailwind writes the role into the utility — .bg-lf-card{background-color:var(--lf-surface-card)} — and emits no --color-lf-card at runtime. The alias exists only in the sources: editing it would change nothing, so the Lab edits the role. The catalogue records the link:

    • Classes. The custom-token class expression covers the role utilities: lf-[a-z0-9-]+, next to libre-*, theme-*, primary* and accent* — TW_CUSTOM_RE in scan-colors.mjs and tw_custom_re in color_inventory.py, changed together. Its prefixes are the palette expression's list, PREFIXES (decision D-a, 15/10/2026): besides bg-, text-, border-, ring-, outline-, divide-, fill-, stroke- and the gradient stops, the side borders (border-t-, -b-, -l-, -r-, -x-, -y-), ring-offset-, shadow-, accent-, caret-, decoration- and placeholder-. So the shadow roles' utilities, shadow-lf-shadow and shadow-lf-shadow-card, count and have their chips. A role name may hold digits, as T's own ROLE_CLASS_RE (frontend/scripts/theme/theme-roles.mjs) allows. A role utility, variants and opacity included (hover:border-lf-card/50), counts among the custom-token classes and enters palette under its alias, --color-lf-<name>.
    • Definitions. A definition inside an @theme inline block gets inline: true and alias_of: the variable it names when its value is exactly var(--x), else null. The two fields are written only for such definitions.
    • Palette. A palette entry gets role when every definition of its variable is an inline alias of one same variable: --color-lf-card → --lf-surface-card. The rule is generic, not tied to the lf prefix.

    Wherever the Lab meets an alias it edits the role — the palette chips and the editor's impact, the export's occurrences, the picker's candidates: each section below says how — and L1, above, writes its overrides where the token blocks define the roles. An alias that is not exactly var(--x) gets no role: see Known Limits.

    🏷️ Test Ids

    The picker says where an element is with the project's own names: its data-testid chain. To write a templated id the way the code writes it, and to find where the code writes it, the scanner indexes the test ids of the sources:

    • In markup (.svelte): data-testid= attributes (via: attr), and the props components render as their data-testid — testid=, testId=, or a name ending in TestId such as optionTestId= or valueTestId= (via: prop). A name that goes on after it, such as testIdPrefix=, is not one. testidValues() reads a quoted value, or the literals of a {…} expression up to its closing brace on the same line.
    • In scripts (a .svelte <script>, .ts, .js): a property or variable whose name ends with testid or testId and takes a literal — testId: 'tab-a', const rowTestId = `row-${id}`, a parameter default (via: script). scriptTestidValues() reads the expression up to the end of the property or statement on the same line. Never a comparison, a …Prefix name, or a type annotation (testId: string holds no literal).
    • Which literals. Only those in value position: at the start of the expression, after ?, :, ??, ||, &&, an arrow => or a grouping ( — never the operands of a comparison, nor the arguments of a call (fn('x')). So {active ? 'tab-on' : 'tab-off'} gives two ids and {x ?? `tab-${id}`} one prefix.
    • Static or templated. A ${…} or {…} cuts the value into a prefix of at least three characters (row-{id} → row-); a value with nothing static before the cut — a pass-through such as {testId} — is not indexable. Static ids go to testids, prefixes to testid_prefixes.
    • In the app tab. virtual:lf-testid-index carries {statics, prefixes}, and only picker/describe.ts imports it: the index rides in the picker's lazy chunk, never in the client. An id of the page that is not static but starts with a known prefix is an instance of a templated id: the selector writes [data-testid^="row-"], the chain and the export row-*.
    • Ids the index does not know are cut by recordPrefix() before their first token that looks like a record: a whole number, or a token with a capital letter — row-42 → row-*, asset-row-42-menu → asset-row-*, kpi-gain-EUR → kpi-gain-* — when at least three characters are left. Digits inside a word do not count (risk-l2-weight stays whole): the project writes its static ids as lower-case kebab words, without capitals. An id with no such token is written as it is.

    Writing prefix* keeps record values — a currency code, a row id — out of the export, and makes the selector reach every instance of the component. The limits of the index are in Known Limits.

    🔬 Finding What Sets a Colour

    picker/describe.ts runs in the app tab. For each colour the designer sees on the element, it reports the computed value and the declaration that sets it: proved, not guessed from selectors.

    The colours read (analyseAll()):

    Property When
    color Always. It is inherited: the search walks up the ancestors (below)
    background-color, background-image The background the designer sees: the element's, or that of the first ancestor whose background is not transparent. background-image only when it holds colours, a gradient
    border-*-color Each visible side: width above 0, style not none or hidden. Four equal sides — same value, same winning declaration — merge into one border-color
    outline-color A visible outline
    text-decoration-color Any text decoration
    fill, stroke SVG elements, unless none
    box-shadow A shadow with colours

    The candidates. collectRules() walks every readable stylesheet but the Lab's own, and keeps the style rules that declare a colour property, each with its cascade layer (utilities; nested layers dotted), the conditions around it and its stylesheet. It enters an @media or @supports block only when its condition holds now, and gives a nested rule an absolute selector (& stands for the parent). For a property, the candidates are:

    • the declaration of every rule the element matches: the longhand, or a shorthand that sets it (SHORTHANDS in cssProps.ts: background, border, border-top, border-color, the logical border-block-* and border-inline-* forms…). The shorthand matters with var(): the CSSOM then leaves the longhand empty, and only the shorthand holds the text;
    • the rules that would match in a state the element is not in — :hover, :focus, :focus-visible, :focus-within, :active, found by stripping those pseudo-classes. They are listed, so the designer sees them, but never tried and never winners;
    • the inline style;
    • the presentation attribute of an SVG element (fill="…", stroke="…", color="…").

    Rules on pseudo-elements (::before, ::placeholder…) are left out: the picker reads the element itself. Each candidate records its text as written, before any Lab change (originalValue() of L2).

    The proof. The candidates are sorted by an estimated cascade order: !important first; then inline styles, rules, attributes; unlayered before layered for normal declarations, the reverse for !important ones; later in the document first. The estimate ignores specificity: the proof settles it. prove() takes the candidates in that order:

    1. it sets the property to a probe colour in the candidate's block, with the same priority: rgb(1, 2, 3) — 0 0 0 1px rgb(1, 2, 3) for a shadow, a gradient of it for an image;
    2. it reads the computed value of the property;
    3. it puts the declaration back exactly, restoring the whole cssText of its block (or the attribute);
    4. the first candidate whose probe changed the computed value is the one that sets it.

    At most 12 candidates are tried per property. All the probing runs in one synchronous task inside withoutTransitions(): a <style data-lf-lab-own> turns transitions off, and styles are flushed before and after. Nothing is painted in between, and no transition starts. The Lab's own specialisation sheet is disabled meanwhile, since a specialisation would win every probe; the property is flagged «already specialised» when one of its rules applies.

    Up the tree. color, fill and stroke are inherited. When the element declares none, or its winner is inherit or unset — Tailwind's preflight writes color: inherit on buttons and inputs — or currentColor for color, the search moves on to the parent, and further up. The property then records the depth, the tag and the nearest test id of the declaring ancestor. A background seen through from an ancestor is recorded the same way. A colour whose winner writes currentColor, or which equals color with no winner, is flagged: it follows the text colour.

    Charts. Inside an ECharts instance ([_echarts_instance_]), the facts add the chart: the selector of its component (its nearest test id, else its CSS path), the colours of its option as the app wrote them — L3's changes undone, at most 40 — and the colour of the shape under the pointer. That colour comes from zrender's hit test, not a documented ECharts API: when it fails, the colour is unknown.

    What the app tab reports (PickedElement in types.ts): the route (SvelteKit's route id, see The Anchor), the theme, the test-id chain (nearest first, at most 8), the CSS path (positions included), the tag, the classes without Svelte's scope class (reported apart), the element's own component selector and, per property, the computed value, its colours, the depth, the declarations with the winner first, and the specialisation selector. Never the element's text.

    🧷 The Specialisation Selector

    A specialisation needs a selector for «this element, in every instance of its component» — decision (a) of 14/10/2026. build() in describe.ts computes one per property, with the helpers of picker/anchor.ts:

    1. Which element. The element that declares the colour, when it sits inside the picked element's component, whose root is the picked element's nearest test id: a header text whose colour the th declares, a card whose background shows through. Above the component — the page, body — the picked element itself.
    2. Where it is. The nearest test id above it — [data-testid="x"], or [data-testid^="prefix"] for an instance of a templated id — then the path down to the element, tag by tag, with child combinators and without positions: the same node of the same template, in every instance. Beyond six segments, the selector keeps the last six, after a descendant combinator. An element with its own test id is that test id alone.
    3. Which classes. On the element, only the classes the winning rule names (selectorNames()): p.text-gray-500 keeps its colour class, while a layout or state class — flex, sorted — neither widens nor narrows the selector. Svelte's scope classes never enter: they change with every build. A selector longer than 400 characters falls back to the test id followed by the element, as a descendant.
    4. No test id around. The element's own CSS path from body, positions included: breadth: element, this element only.

    Next to Specialise here, the Lab shows the selector and how many elements it matched on the open page when the element was picked (countMatches()). That count is the check. In the first live test, a design that wrote the test id, the tag and all the element's classes took 52 elements for a layout div inside a header cell of the transactions table, body cells included. The shipped design specialises the th that declares the colour, and takes the 12 header cells, nothing else:

    [data-testid="tx-table"] > div > div > table > thead > tr > th

    ⚠️ Known Limits

    • By value, not by meaning. Until colours become tokens, a change reaches every place that writes the value (problem P5 of the colour analysis): the spike found the same #64748b in 33 rules of /transactions — a modal, the pagination, the data table. The editor lists the occurrences, and a stylesheet colour can go down to one occurrence; a chart colour cannot, because an ECharts option carries no provenance. The export lists the catalogue's occurrences for both. A specialisation narrows either to one component, chart colours included. The fixed colours of the chart categories are the exception: the Categories tab changes them by key (Chart Categories).
    • ECharts' default palette (#5070dd, …) is not written in the app's sources: it is not in the catalogue, and the Lab does not offer it.
    • Derived and generated colours. A colour computed before setOption — a shade derived from a literal (familyShade, the GR4 shades), an HSL generated from an index (getIndexColor, lotColor) — reaches the option as a value no change targets. The preview changes a base colour only where the option carries it unchanged; the export still points at the literal in the source. The shades of a chart category are the exception: they are mixed from what categoryColor returns, so a category change reaches them.
    • No preview for the proposal layer.
    • Variables redefined in a subtree. L1 writes its overrides on <html> and on the .light and .dark subtrees (VAR_SELECTOR in engine/vars.ts), where the token blocks of tokens.css define the roles: a theme island that redefines the roles takes the override too. A definition under any other selector — a component's own — is rewritten by L2 instead; only one in a style attribute, which no engine rewrites, keeps its value for its subtree, as the nearer definition. Conversely, L1 runs in the app tabs without the catalogue (designerLabImports.gate.test.ts lets only the Lab page import it), so its selectors are the same for every variable: it cannot know where each one is defined. A variable the app defines on <html> only — a --theme-* of app.css, a palette shade — thus also gets a one-theme override inside a .light or .dark island of that theme placed in the other theme, where the code does not redefine it: the preview there shows a value the edited definition would not reach. Today no element but <html> carries light or dark (themeStore.ts and the inline script of app.html set them on document.documentElement), so no such island exists yet.
    • Inline aliases that are not var(--x). An @theme inline alias with any other value — a color-mix(), say — gets no role (Colour Roles): its chip edits the alias itself, a variable that does not exist at runtime, so nothing changes. Edit the roles it mixes. tokens.css has none today.
    • Other color-mix() values. The editor reads a mix with transparent, the A slider's form, but not a mix of two colours, nor one whose two percentages do not add up to 100: for such a value it shows Unrecognised colour and no sliders, and keeps Apply disabled until a new value — typed, from the sRGB input or snapped to a variable — replaces it.
    • Class names in comments count as uses, in the scanner and in the Python inventory alike: the header comments of app.css and tokens.css name role utilities (bg-lf-card, text-lf-muted…; shadow-lf-shadow-card is written only there). They show among the uses, in the editor's impact, and among the export's occurrences, where an agent finds a comment line.
    • Wide gamut. Stylesheets keep the value as typed, so an oklch() outside sRGB stays wide; charts receive it clamped to sRGB. The editor warns when a value leaves sRGB. <input type="color"> and the gallery screenshots are sRGB only, so a wide-gamut display shows such colours more saturated than the PNGs.
    • Late stylesheets and the redraw signal. A stylesheet that arrives after the state is applied — a route's CSS — is rewritten when it loads, without a redraw signal of its own: a variable it defines that a chart reads at its draw would wait for the chart's next draw. The roles chartRoles reads are all defined in tokens.css, which app.css imports: the global sheet, not a route's.

    The chart categories:

    • The picker does not name a slice's category. It reports the colour of a pie slice as a chart colour, and one value can belong to two categories: open the category from the Categories tab. While a category change applies, the slice reports the edited colour, not the table's. Naming the category is in L's backlog.
    • Translucent category colours. For a translucent value the engine answers rgba(), and the charts draw the category with it. Its GR4 subtype shades, though, are mixed from the colour alone — familyShade reads the channels and drops the alpha — so they come out opaque.
    • bucket:Unknown and keys outside the tables. An edit of bucket:Unknown reaches the categories the tables call Unknown, of both kinds, and the charts that ask for Unknown by name (the unclassified countries of the allocation history). categoryColor also draws a key outside its tables in the Unknown colour, but the edit does not reach such a key: it keeps the table's colour. The enum gates keep such keys out of real data.

    The element picker:

    • Pointer-transparent elements. document.elementsFromPoint() skips elements with pointer-events: none: such an element cannot be picked, and the element under it is picked instead.
    • Resting colours only. Rules for :hover, :focus or :active are listed with the declarations but never proved, and cannot be specialised; pseudo-elements (::before, ::placeholder) are not read.
    • Conditions not evaluated. @container, @scope and the other grouping rules are walked without evaluating their condition, which is only recorded: the probe decides whether the declaration applies.
    • Rules that do not compare. The selector of a nested or wrapped rule does not match the catalogue's after normalisation: the candidates fall back to the colour's literals in the component's files.
    • A structural selector. The path below the test id is exact for today's DOM: a wrapper added later breaks the preview selector. The export keeps the candidates and the test ids, which verify-export checks.
    • Backgrounds from outside. A background seen through from outside the component cannot be specialised: edit the source.
    • Shadows and gradients are reported, not specialised.
    • Inline !important beats a specialisation, as it beats every rule.
    • Svelte scope classes never enter a selector: they change with every build. The anchor reports the element's scope class apart, as context.
    • Lower-case values in unknown ids. The index covers the markup's test-id attributes and props and the scripts' …testId properties and variables; an id it does not know is cut before its first number or capitalised token. A data value inside such an id that is a lower-case word — no digit, no capital — cannot be told from the code's own words: the chain, the selector and the export write it as it is.

    📥 Import

    Import reads an export back (parseImport() in export.ts):

    • it requires the schema lf-designer-lab/1; a change with an unknown layer or scope, or an unsafe to, is reported and skipped;
    • a specialisation (element) is skipped as invalid unless its selector passes isSafeSelector(), its property is one a specialisation can set, and a chart one carries a color_key (#rrggbb or oklch(…));
    • a category change is skipped as an unknown category unless its target has a safe shape — type:, sector: or bucket:, then at most 60 letters, digits, spaces or _&.- — and names a category of the running catalogue;
    • an anchor, on any layer, goes through sanitizeAnchor(), which keeps only the shape and the sizes the Lab writes: one-line strings within limits (route 300 characters, selectors 600, at most 8 test ids, 40 classes and 20 candidates), the enums (theme, breadth, source.kind, why), positive line numbers and a --name for source.var. An anchor without a readable route, safe selector, property or tag is dropped with a warning; the change is kept;
    • it warns when catalog_hash differs from the running catalogue: the code changed since the export;
    • it finds a single-occurrence css-literal change again by file, line and raw value; when that occurrence is gone, the change falls back to every occurrence of the value, with a warning;
    • it keeps one change per id, as the Lab does: a repeated change replaces the earlier one, in its place, with a warning;
    • the imported changes replace the current ones; notes, author and variants come from the file when it has them.

    ✅ Verifying an Export

    verify-export.mjs checks an export against the code as it is now:

    node frontend/scripts/designer-lab/verify-export.mjs designer-lab-changes.json          # human summary
node frontend/scripts/designer-lab/verify-export.mjs designer-lab-changes.json --json   # lf-designer-lab-verify/1 report

    It rebuilds the catalogue to compare its hash with catalog_hash, then looks for every occurrence on its file:line, case-insensitively. The text it looks for is the occurrence's raw when it has one — a literal, or the class of a role utility — else, for a css-var change, the family-shade of its --color-* target (emerald-600), for a Tailwind class use. Each occurrence is:

    • ok: still there;
    • moved: elsewhere in the same file, reported with the nearest line;
    • missing: nowhere in the file.

    Variable definitions are checked the same way, and value_now reports a definition whose value changed since the export. --root <dir> checks another frontend/ tree. An export is input: a path that leaves the checked tree (../../etc/hosts) is never read, and counts as missing (as gone, for a candidate).

    Specialisations and anchors. The candidates of an element change are located the same way, on their raw text, but counted apart — candidates_ok, candidates_moved, candidates_missing: a candidate that moved or is gone is a hint, not an error. Every change with an anchor, and every element change, gets an anchor.status:

    anchor.status Meaning
    ok For a specialisation, at least one candidate is still there; and every test id of the anchor is still written in the code
    testid-missing A test id of the anchor is no longer written — listed in testids_missing; the component moved or was renamed. A warning
    no-candidates A specialisation that lists no candidate: the agent binds it by test id
    lost A specialisation none of whose candidates is still there, in place or moved: exit code 1

    no-candidates and lost come first; testid-missing only when neither applies. The test ids are checked against the rebuilt catalogue (testidKnown()): a static id must still be written, or produced by a known prefix; a prefix* is known when it extends a catalogue prefix, or when static ids start with it — the picker may have cut an id the index did not know. The totals add anchors_lost and anchor_testids_missing, and the human summary a line for the specialisations.

    Chart categories. The occurrences of a category change are found by key and theme, never by value (locateCategory()): categories share values, and a search for the value could land on another category's line. categoryLines() of the scanner reads the occurrence's file, and the line that writes the change's target in the occurrence's theme_context decides. The occurrence is ok when that is its own line, moved when the key and theme are written on another line now (reported with that line), and missing when the key is gone or its line holds a value other than raw: the export's starting value is stale.

    Exit code Meaning
    0 Nothing is missing and no specialisation is lost: moved occurrences, moved or gone candidates, testid-missing and no-candidates are fine
    1 At least one occurrence is missing, or a specialisation is lost
    2 Bad input: no file, not JSON, or not an lf-designer-lab/1 export

    🤖 The Skill designer-lab-apply

    .github/skills/design-tools/designer-lab-apply/SKILL.md tells an agent how to apply an export:

    1. verify it with verify-export.mjs;
    2. group the changes by layer;
    3. apply them occurrence by occurrence — never a blind replace of a value everywhere — respecting scope and theme_context, and the owners of app.css and of the token files;
    4. prove the effect with a same-day gallery diff (scripts/visual_review/README.md);
    5. report every change, including those not applied and why.

    A specialisation (element) leaves the shared source as it is: the agent creates a component-scoped variable, or a role token, and binds it at the places the candidates list. The selector in target is the preview's, context rather than code to paste; since no element text is exported, the component is found by route, test ids and CSS path, never by content.

    A category change is applied on the lines its occurrences[] list in chartCategories.ts, one per theme of the change, and never by value: another category, a role or another chart may write the same value. The subtype shades follow the new colour by themselves, and a bucket change edits the one entry both kinds share.

    Changing how the app looks is a decision: an agent applies an export only when the developer asks, in a workstream allowed to change the appearance.

    🎨 The Lab Never Repaints Itself

    The Lab's own colours reach the page only as --lab-* custom properties in the inline style of its root element (labTheme.ts, one set for light and one for dark, following the class of <html>). Its stylesheets hold no colour, only var(--lab-*), and its markup uses no Tailwind colour class. The engines rewrite stylesheet rules and the variables of <html> and of the .light/.dark subtrees — classes the Lab's markup never carries — never an inline style, so editing the app's colours never repaints the Lab. Specialisation rules aim at the app's elements: a component selector starts from an app test id, which the Lab's markup never carries. The colour-vision filter sits on <html> and applies to the Lab as well.

After changing the scanner or the plugin, or LF_DESIGNER_LAB, force a rebuild (./dev.py server --test --rebuild, or ./dev.py front build --debug).
