    ⚙️ Settings Components

    This section documents the components used for the Settings pages (User Preferences, Global Settings, Profile, Users, Security).

    🏗️ Architecture

    The settings system uses a modular architecture based on a common layout and reusable field components.

    🗂️ Tab registry

    The tabs of the Settings page are a registry: SETTINGS_TABS in lib/features/settings/settingsTabs.ts. routes/(app)/settings/[...path]/+page.svelte names no tab itself: it draws its two bars and the active body from that list. Each entry is a SettingsTab:

    Field Role
    id The suffix of its settings-tab-{id} test id, and the ?tab= value of 1.2, still read
    path Its address (lot B10), from the table of settingsPaths.ts: /settings/<tab>, or /settings/admin/<tab> for a member of Administration
    labelKey Catalogue key of the label, drawn as $_(labelKey) on the tab and in the heading shown on a phone
    icon Lucide icon of the tab button
    order Position in the bar, left to right; for a member of a group, in the group's second bar
    component The tab body
    visible?(ctx) Who sees the tab; when absent, everyone does
    props?(ctx) Props spread on the body
    group? The id of the group of SETTINGS_TAB_GROUPS the tab belongs to: the top bar shows the group as one entry, and a second bar lists its members
    badge?(ctx) The number its button shows, none for 0; a group's entry shows the sum of its visible members'
    prefetch?(ctx) What the page starts loading before the tab is opened, so that badge can count: run when the page opens, and again when the context changes, for every visible tab that has one
    alignEnd? On a wide screen, starts the right-hand side: this entry and every entry after it sit on the right (sm:ml-auto on its button). One tab or one group carries it: today the administration group, and no tab

    ctx is a SettingsTabContext, {isSuperuser}, which the page derives from the auth store ($auth.user?.is_superuser ?? false). The registry holds nine tabs:

    id order Body Visible to group Extras
    profile 10 ProfileTab everyone — —
    preferences 20 PreferencesTab everyone — —
    plugins 25 PluginSettingsTab everyone — —
    about 30 AboutTab everyone — —
    admin 100 GlobalSettingsTab administrators administration Label settings.globalSettings (Global Settings), icon Settings2; visible: (ctx) => ctx.isSuperuser (lot N69-2, decision D4 a); props: (ctx) => ({canEdit: ctx.isSuperuser}), kept: see GlobalSettingsTab
    users 110 UsersTab administrators administration visible: (ctx) => ctx.isSuperuser
    backup 120 BackupTab administrators administration visible: (ctx) => ctx.isSuperuser
    email 130 EmailSettingsTab administrators administration visible: (ctx) => ctx.isSuperuser
    security 140 SecurityTab administrators administration visible: (ctx) => ctx.isSuperuser; badge: () => securityChecks.attentionCount; prefetch: (ctx) => { if (ctx.isSuperuser) void securityChecks.ensureLoaded(); }

    The admin id stays as it was, so ?tab=admin, the link of the open-registration warning, still opens the global settings (the warning shows to administrators only, as the tab does; for a regular user, ?tab=admin names a hidden tab and opens profile, the first visible one); lot A8b changed only its label and its icon, the group having taken the Shield, and removed the key settings.admin (Admin) from the catalogues. Five bodies are in lib/features/settings/tabs/, the Security tab's in lib/features/settings/security/ (SecurityTab). The Plugins tab's body, lib/features/plugin-settings/PluginSettingsTab.svelte (label pluginSettings.tab.label), the Backup tab's, lib/features/backup/BackupTab.svelte (label backup.tab), and the Email tab's, lib/features/email/EmailSettingsTab.svelte (label email.tab.label), live with their features: for the Plugins tab see Plugin Settings › The Interface, for the Email tab The Email Tab. The Plugins tab takes no props: every user sees it, and the catalogue the API returns already says which fields this user may change.

    Groups

    SETTINGS_TAB_GROUPS, in the same module, holds the groups of the top bar (decision P13 b), each a SettingsTabGroup, {id, labelKey, icon, alignEnd?}. There is one today, administration: label settings.administration (Administration), icon Shield, alignEnd: true. Its members are admin, users, backup, email and security; profile, preferences, plugins and about belong to no group. A group's id is a ?tab= value and a test-id suffix too (settings-tab-administration): it is URL-safe, and no tab's id.

    settingsBar(tabs, groups, ctx) gives the entries of the top bar, SettingsBarEntry[], as a new array, and leaves the lists it is given as they were: the tabs of visibleSettingsTabs(tabs, ctx), by order, each a {kind: 'tab', tab} entry, except the visible members of a group, gathered into one {kind: 'group', group, members} entry placed where its first visible member would be, members being its visible members by order. A group without a visible member has no entry, and a tab whose group names none of groups stays a tab entry. A regular user's bar is profile, preferences, plugins and about: every member of administration is an administrator's (since lot N69-2), so the group has no entry for them; an administrator's ends with administration and its five members.

    The page

    The page is the runtime of the registry, written in Svelte 5 runes:

    • Top bar: settingsBar(SETTINGS_TABS, SETTINGS_TAB_GROUPS, ctx), handed to TabBar with the labels hidden on a phone (hideLabelOnMobile). A tab entry is drawn as its tab (settings-tab-{id}, its icon, $_(labelKey)); a group entry with the group's icon and label, and the test id settings-tab-{groupId}. An entry whose tab or group has alignEnd gets sm:ml-auto. The top bar selects the entry of the open tab: the tab itself, or the group of the open member.
    • Second bar: while the open tab is a member of a group with at least two visible members, a second TabBar, inside data-testid="settings-subtabs", lists those members, each with its own settings-tab-{id}, icon, label (hidden on a phone too) and badge, the open one selected. It takes the same props (hideLabelOnMobile, scrollable) and the same colour roles as the top bar. A group with one visible member gets no second bar: its entry opens that member directly, and the member has no settings-tab-{id} of its own. No context of today's registry makes such a group since lot N69-2 (a regular user sees no member of administration, an administrator all five), but the page still handles it, on a registry of the test's own (see the tests below).
    • Clicks (selectTop()): a tab entry opens its tab; a group entry opens the group's first visible member, unless one of its members is open already, which stays, its body not mounted again. A member of the second bar opens that member.
    • Both bars are scrollable: entries that do not fit the card (French or Spanish on a narrow screen) scroll sideways instead of being clipped by its overflow-hidden, the active one stays whole in view, and the sides that hide entries fade (see Scrollable tab bar).
    • Body: the active tab's component alone, with props(ctx) spread on it. The spread is live: when the auth store changes, the body on screen receives the new props. The heading shown on a phone names the active tab, a member and never its group: Global Settings, not Administration.
    • Addresses (lot B10): every tab has one, path, and every group too (/settings/admin). One route, settings/[...path], serves them all, /settings included. settingsPlaceOf(pathname, tabs, groups) reads an address back: the page, a tab, a group, or nothing the registry knows. An address opens its tab at the first render and whenever it changes (Back, Forward, a link); a group's address opens its first visible member. Choosing a tab writes its address with goto(path, {noScroll, keepFocus}), as a new entry of the history. /settings opens the first tab and keeps its address. An unknown address, or the address of a tab this user cannot see once the user is known, goes back to /settings (replaceState). Links never write an address by hand: settingsTabHref(id, query?) of settingsPaths.ts, a module that imports no tab body.
    • Active tab: always a tab, never a group. At /settings, the first visible tab, unless the ?tab= of 1.2 names a visible tab or a group; the address then becomes the tab's own (replaceState): a member's id opens that member inside its group (with the second bar when the group has two visible members or more), a group's id its first visible member (?tab=administration opens admin, for an administrator). The choice runs in $effect.pre, so the tab that ?tab= names is the first body mounted: the default body never mounts, not even for an instant. A ?tab= value is applied once: a later page update that keeps it does not take back the tab the user picked, while a new value, or the same one after a tab's address, is applied again. An unknown id, the id of a tab this user cannot see, or that of a group with no visible member, is ignored: a regular user's ?tab=admin or ?tab=administration opens profile, and the body of Global Settings never mounts for them. A ?tab= naming a tab that becomes visible later (the user is promoted while on the page) is applied when the tab appears, inside its group. If the active tab stops being visible, the first visible tab opens.
    • Badges: a tab entry shows its badge(ctx), a group entry the sum of its visible members', and TabBar draws none for 0. They are read while the bars are derived, so a badge follows the reactive state it reads: a count that arrives after the first render shows at once.
    • Prefetch: an $effect calls the prefetch(ctx) of every visible tab that has one, when the page mounts and again whenever the context changes (a promotion included, which prefetches the tab that has just appeared); never for a tab this context does not show. The calls run inside untrack(): a prefetch reads the state it fills (ensureLoaded() reads the security checks' status), and a tracked read would run the effect again each time that state moves — after a failure, a new request, in a loop. So nothing else prefetches again: not a change of tab, of group or of ?tab=, nor a change of the state a prefetch reads.

    Adding a tab takes one entry in SETTINGS_TABS, plus the import of its body. The users entry, a tab only administrators see, in the administration group, is a complete example:

    import {Users} from 'lucide-svelte';
import UsersTab from '$lib/features/settings/tabs/UsersTab.svelte';

export const SETTINGS_TABS: readonly SettingsTab[] = [
    // profile (10), preferences (20), plugins (25), about (30), admin (100, administration)
    // Administrators only: the accounts (decision D-A10) and every account link (lot UA3).
    {id: 'users', labelKey: 'settings.users', icon: Users, order: 110, component: UsersTab, visible: (ctx) => ctx.isSuperuser, group: 'administration'},
];
    • order: a free number between the neighbours. The orders leave gaps, so no other tab is renumbered; 110 puts users after Global Settings (100) in the group's second bar. A tab without a group and with an order between 30 and 100 lands after About, on the left; above 100, after the group's entry, which sits where its first member (100) would be, so on the right. Every order is unique.
    • visible: (ctx) => ctx.isSuperuser keeps the tab out of a regular user's bars altogether, and a ?tab= naming it is ignored for them. Leave visible out for a tab everyone sees.
    • group: 'administration' for a tab that looks after the instance: it has no button of its own in the top bar, and shows in the group's second bar. Leave it out for a tab of the top bar.
    • props: only when the body depends on the context, as admin does for canEdit. Since lot N69-2 only administrators see that tab, so canEdit is always true on screen: the read-only branch, canEdit: false, stays in GlobalSettingsTab, unreached from the interface, until a cleanup.
    • badge and prefetch: only for a tab whose button counts something, today security alone. badge reads a reactive count synchronously, 0 until there is one; prefetch starts what the count needs, does nothing for a context the tab is not for, and nothing again once loaded, as securityChecks.ensureLoaded() does.
    • alignEnd: one tab or one group carries it, today the administration group; no tab does, though the page still honours a tab's.
    • id and labelKey: the id is unique, made of lowercase letters, digits and dashes, starts with a letter, and is no group's id; the labelKey is a sentence in all four catalogues.
    • Tests: lib/features/settings/settingsTabs.test.ts pins the content of the registry through its TODAY table, so the new tab adds its row there in the same change, its id to the CONTEXTS and BARS lists of those who see it and, when it joins the group, to ADMINISTRATION, with a vi.mock of its body module like the others; the cases that list today's tabs by name follow it (users also has two cases of its own: STAB-01, hidden from a regular user, and STAB-02, order 110 after admin, both members of the group; admin has one, rewritten by lot N69-2: hidden from a regular user, shown to an administrator, its props still {canEdit: isSuperuser}). The same file checks the ids, the orders and the labels in the four catalogues, the group and what its tabs carry (STAB-03 to STAB-14: one group, its label, icon and members, no tab with alignEnd, security the only tab with a badge and a prefetch, the bar of each context; STAB-14, lot N69-2: no administration entry nor any of its members in a regular user's bar, the entry once in an administrator's, admin its first member), and settingsBar() on lists of its own (SBAR-01 to SBAR-05). routes/(app)/settings/page.tabs.test.ts tests the page on a registry of its own, with two groups (crew, and office, the stand-in for Administration as lot A8b had it, with one visible member for a regular user) and counts in a reactive box (SPAGE-01 to SPAGE-21: the top bar, the second bar and its clicks, ?tab= naming a member or a group, the badges and their sums, the prefetch at the start, again for a new context and never otherwise). SPAGE-22 to SPAGE-24 (lot N69-2) render the page on the real registry: a regular user's page with neither settings-tab-administration nor settings-tab-admin, Profile open; ?tab=admin and ?tab=administration opening Profile for a regular user, the Global Settings body never mounted, and Global Settings, with canEdit: true, inside its group for an administrator. The file loads the real settingsTabs module (importOriginal), which imports every body: the mocked module's SETTINGS_TABS and SETTINGS_TAB_GROUPS are getters, answering the real lists while a case sets mocks.registry.real and the synthetic ones otherwise, and each real body is a probe named by its module (mocks.realBodies). A new tab adds its body there, with its vi.mock (a store the registry imports gets a no-op stand-in, as securityChecks does). ./dev.py test front-utility core-unit runs settingsTabs.test.ts, ./dev.py test front-utility component-unit runs page.tabs.test.ts.

    📐 SettingsLayout

    The SettingsLayout component provides the structural shell for all settings tabs.

    Features:

    • Two-Column Layout: Sidebar navigation on the left, content on the right.
    • Global Actions: "Save All", "Undo All", "Reset All" buttons in the header.
    • Lock Toggle: Optional lock button for admin settings (prevents accidental edits).
    • Responsive: Stacks vertically on mobile.

    Props:

    • categories: Array of { id, icon, labelKey } for the sidebar.
    • selectedCategory: ID of the currently active category filter.
    • hasChanges: Boolean to show Save/Undo buttons.
    • hasNonDefaults: Boolean to show Reset button.
    • isLocked: Boolean state of the edit lock.

    🎨 PreferencesTab

    Manages user-specific settings (Language, Currency, Theme) and hosts the Onboarding category described below. Its categories are display (Language), currency (Default Currency), appearance (Theme) and onboarding, plus All Settings when none is selected.

    Logic (lib/features/settings/tabs/PreferencesTab.svelte):

    1. Load: Fetches Global Defaults (/settings/global) and User Settings (/settings/user) in parallel.
    2. State Tracking:
      • originalValues: The values currently saved in the DB.
      • editedValues: The values currently in the form inputs.
      • globalDefaults: The system-wide default values — FALLBACK_DEFAULTS (en, EUR, auto) when /settings/global cannot be loaded.
    3. Computed States:
      • isModified: editedValues !== originalValues (Shows Save/Undo).
      • isNonDefault: originalValues !== globalDefaults (Shows Reset, but only while the field has no pending edit: SettingActions.svelte).
    4. Persistence: Saves to /settings/user via PUT, one field per request. Save sends that field; Save All sends the modified fields one after the other, then reports what was saved and what failed in a single toast (success, partial or error). Language and theme take effect only once their write succeeds (currentLanguage.set(), applyTheme()), and userSettings.setDirect() then writes the saved language, currency and theme into the store. Reset only copies the global default into editedValues: it still has to be saved.

    The Default Currency (base_currency) is proposed when something new is created: BrokerForm.svelte uses it for the first initial balance, AssetModal.svelte for a new asset's currency and PacPlannerTool.svelte for a new plan's valuation currency. The Dashboard, the Brokers list and detail pages, and the risk panel of the Assets page start their display currency from the global default_currency ($globalSettings) instead.

    🧭 OnboardingReplaySection

    OnboardingReplaySection.svelte (in frontend/src/lib/features/onboarding/components/) is the Onboarding category of PreferencesTab ({id: 'onboarding', icon: Compass, labelKey: 'onboarding.settings.category'}). The tab renders it when that category is selected and in the All Settings view (no category selected). It lists every onboarding flow with its progress and lets the user replay any of them without changing that recorded progress.     match, mismatch, unverifiable The verdict of the check

    🔧 Field Components

    Each setting type has a specialized component that handles its own UI and events.

    • SettingSelect: Generic dropdown (uses SimpleSelect).
    • SettingCurrency: Searchable currency selector (uses SearchSelect).
    • SettingTheme: Radio buttons for Light/Dark/Auto theme with visual preview.
    • SettingNumber: Numeric input with increment/decrement.
    • SettingToggle: Boolean toggle switch.

    Common Props for Field Components:

    • value: Two-way bound value.
    • label: Field label.
    • hint: Helper text.
    • isModified: Highlights the field if changed.
    • isNonDefault: Shows a "Reset to Default" indicator.
    • isLocked: Disables input.

    The three wrappers shared with the Global Settings tab — SettingSelect, SettingCurrency, SettingTheme — also accept embedded: when true, the row drops its own padding and bottom border so it can sit inside a parent card without a double separator. The standalone Preferences tab renders rows in a list and keeps the default; the Global Settings tab embeds the shared wrappers in its own per-setting cards and passes embedded.

    💻 Usage Example

    Both components take callback props (onsaveAll, onundoAll, onresetAll on the layout; onsave, onundo, onreset on a field), not component events:

    <script lang="ts">
  import SettingsLayout from '$lib/features/settings/SettingsLayout.svelte';
  import SettingSelect from '$lib/features/settings/SettingSelect.svelte';

  let original = $state('option1');
  let value = $state('option1');
  let hasChanges = $derived(value !== original);

  function save() {
    // persist `value`, then:
    original = value;
  }
</script>

<SettingsLayout title="My Settings" {hasChanges} onsaveAll={save} onundoAll={() => (value = original)}>
  <SettingSelect
    bind:value
    label="Choose Option"
    options={[{value: 'option1', label: 'One'}]}
    isModified={hasChanges}
    onsave={save}
    onundo={() => (value = original)}
  />
</SettingsLayout>
